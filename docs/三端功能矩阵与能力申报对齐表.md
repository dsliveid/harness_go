> 状态：**权威真相源（Single Source of Truth）**。任何「这个功能该在哪端做 / 该申报什么标签」的争议，一律以本表为准。
> 上游依据：`docs/protocols.md` §6（设备协议）、`pkg/toolapi/spec.go:93-106`（能力常量）、`internal/model/device.go:9-13`（设备形态枚举）、`internal/apperr/apperr.go:78-105`（fs / device 错误码）。
> 姊妹文档：`docs/桌面端架构与功能设计.md`、`docs/移动端架构与功能设计.md`、`docs/工作区宿主与目录选择对接约定.md`。

## 0. 为什么需要这张表

三端并行开发最容易出的不是技术问题，而是**同一件事在三处各写一遍、并且写得不一样**：

- 桌面端以为移动端能执行文件操作 → 降级路径写成「移动端兜底」，结果线上崩；
- 移动端申报了自己做不到的能力 → 前端把空间显示为可用，用户点了必然失败；
- 三端自造能力标签 → 服务端 `capabilities` 表里出现 5 种拼写。

本表用**已存在的常量词汇**锁定三端边界，新增任何能力必须先改本表 + `pkg/toolapi` 常量 + `docs/protocols.md`，禁止在端侧先写后补。

## 4. 能力申报对照（三端 `capabilities[]` 标准形态）

> 申报入口唯一：`POST /api/v1/devices/pair`（`internal/api/device_handler.go:46` 的 `capabilityInput`，**只接受 `name` / `version`**，禁止客户端指定 `device_id`），以及每次 `ping` 的 `capabilities_hash`。

### 4.1 桌面端（`kind=desktop`）

```json
[
  { "name": "workspace.list",  "version": "1" },
  { "name": "workspace.read",  "version": "1" },
  { "name": "workspace.write", "version": "1" },
  { "name": "process",         "version": "1" },
  { "name": "network",         "version": "1" }
]
```

### 4.2 移动端（`kind=mobile` / `tablet`）

```json
[
  { "name": "network", "version": "1" }
]
```

- MM1–MM3 阶段：**只申报 `network`**（HTTP 类轻执行 + 会话与审批走服务端 API）；
- MM4 若实现 App 沙箱目录列举，再加 `{ "name": "workspace.list", "version": "1" }`；
- **永不申报** `process` / `workspace.read` / `workspace.write`。

### 4.3 浏览器端

浏览器端不作为执行设备注册，**不申报任何能力**（走用户令牌 + HTTP/SSE）。若启用 localhost 桥接入桌面 Runner，仍由**桌面端**申报能力，浏览器只是调用方。

### 4.4 CLI / headless Runner（`kind=cli`）

```json
[
  { "name": "workspace.list",  "version": "1" },
  { "name": "workspace.read",  "version": "1" },
  { "name": "workspace.write", "version": "1" },
  { "name": "process",         "version": "1" },
  { "name": "network",         "version": "1" }
]
```

## 5. 降级矩阵（端侧缺席时谁兜底）

铁律：**任何端掉线，服务端必须能兜底**（可行性方案 §4.2 不变量 5）。若某能力服务端兜不了，该能力就**不能**设计成「只有端能做」。

| 能力 | 端侧缺席时 | 用户可见结果 | 依据 |
| --- | --- | --- | --- |
| **发起对话（Run）** | ❌ **不降级**：归属设备离线 → **拒绝发起 Run**（`409` + 设备离线专用错误码），仅可查看历史 | 明确报错「设备已离线，请先让设备上线」；消息不落库、模型不被调用 | 本仓 `docs/下一步工作计划-工作空间严格绑定派发改造.md` §0.1 R2 |
| **进行中 Run** | ❌ **自动中断**：设备离线事件触发，取消该设备上所有进行中 Run | Run 状态置 `cancelled` + 明确文案 | 同上 R3（`hub.go` `OnOffline` + `run_service.StopRun`） |
| 目录列举 `fs.list` | ⚠️ **不降级**：返回 `fs.host_offline`，前端提示该工作空间离线 | 明确报错（**不得**换成服务端目录，否则会选错盘） | 工作区宿主约定 §5 L1 |
| 端侧工具（`executor=device`） | ✅ 静默降级 `executor=server` | 无感（不报错） | protocols.md §6.2 |
| 端侧真实执行失败/超时 | ❌ 不重跑本地（防二次副作用） | 采信端侧终态 | protocols.md §6.2 |
| 审批决策 | ✅ 服务端 REST 可批（`strict_approval_device=false`） | 无感 | protocols.md §6.4 |
| 审批决策（`strict_approval_device=true` 且指定了别的设备） | ❌ 拒绝 | 403 `approval.device_mismatch` | protocols.md §6.4 |
| 推送通知（移动端缺席） | ✅ 站内消息 / 浏览器端可见 | 延迟可见 | — |
| 会话写权（租约） | ✅ 服务端本地可写（`holder=""`、`epoch=0`） | 无感 | protocols.md §6.3 |
| 文件投递 | ❌ 需端在线 | 队列等待 | — |

> ⚠️ 特别注意：**目录列举是唯一「禁止降级」的能力**。这是本设计最关键的一条——降级会把「某客户端空间」的目录列成「服务端目录」，用户会把项目建到错误的机器上。

## 6. 错误码对照（三端必须一致处理）

来自 `internal/apperr/apperr.go:78-105`：

| 错误码 | 触发 | 前端表现 | 端侧动作 |
| --- | --- | --- | --- |
| `fs.path_denied` | 路径越界/非法 | 输入框标红 + 提示 | 端侧拒绝并上报 |
| `fs.path_not_found` | 路径不存在或非目录 | 提示重选 | — |
| `fs.host_offline` | 指定宿主不在线 | **不降级**，提示离线 | 重连后恢复 |
| `fs.host_unsupported` | 宿主未申报 `workspace.list` | 空间置灰 | 补申报后重连 |
| `fs.host_timeout` | 端侧 3s 未应答 | 提示重试 | 3s 硬超时自守 |
| `device.pair_code_invalid` | 码不存在/已消费/已过期 | 统一提示（防枚举） | — |
| `device.not_found` | 设备不存在 | 刷新列表 | — |
| `device.revoked` | 设备被吊销 | 提示重新配对 | **停止重连** |
| `device.protocol_mismatch` | 版本不兼容 | 提示升级 | **停止重连** |
| `device.disabled` | 服务端关闭设备域 | 提示不可用 | 停止重连 |

## 8. 变更流程（新增能力必须走完）

1. 在 `pkg/toolapi/spec.go` 增加能力常量（或复用已有常量）；
2. 在 `docs/protocols.md` §1.1 词表登记语义；
3. 更新本表 §2（词表）、§3（三端归属）、§4（申报形态）、§5（降级策略）；
4. 在对应端设计文档的里程碑补验收项；
5. 最后才允许端侧代码引用该标签。

> 反例（必须拒绝的提法）：「先在移动端把 `workspace.read` 加上，服务端常量后面补」——一旦上线，服务端 `capabilities` 表就出现无定义的标签，前端判断逻辑会静默失效。

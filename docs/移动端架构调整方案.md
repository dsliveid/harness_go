## 0. 一页纸结论

| # | 结论 |
| --- | --- |
| 1 | 移动端定位从「遥控器 + 审批中心 + 轻执行」改为 **「WebView 为主体的轻客户端」** |

| 9 | 本阶段**只出架构文档，不改动任何代码** |

## 1. 新定位与差异声明

### 1.1 旧定位为什么被推翻

`docs/移动端架构与功能设计.md` §1.1 的定位推导基于三个独占优势：

1. 人总是带着手机 → **审批不必守在电脑前**
2. 推送是唯一能穿透「App 未运行」的通道
3. 相机/相册是手机独有输入

**第 1 条已不再成立**，原因有三：

| 原因 | 依据 |
| --- | --- |
| 审批需要上下文，手机端拿不到 | 原生审批页只有工具名/风险/摘要/args；Web 侧 `ApprovalBar.tsx` 同屏还有消息流、推理卡、数据范围说明 |
| 服务端默认把浏览器当可审通道 | `internal/approval/gate.go:182`：`strict=false（默认）→ 只做审计，恒 Allowed（避免把浏览器端用户锁死）` |
| WebView 已经能审 | 走 WebView 即可获得完整上下文，无需原生重写 |

**第 2、3 条仍然成立**，因此保留推送与相册能力。

### 1.2 新定位（一句话）

> **移动端是一个「能装下服务端 Web UI 的壳」+ 必要的平台能力桥接。**
> 它不自建对话界面，不自建审批界面，不参与任何执行面判定。

### 1.3 与旧文档的差异声明

| 旧文档章节 | 旧口径 | 新口径 | 处理 |
| --- | --- | --- | --- |

## 4. 关键链路设计

### 4.1 WebView 成为主体

**职责**：加载服务端 Web UI（`//go:embed web/dist` 那一套），承载对话、图片上传、审批状态查看等全部交互。

**保留的三条既有工程红线**（`webview_page.dart:6-12`，继续有效）：

1. **不注入令牌**（R3）→ 强化为 R9，改用 Cookie / ticket 交换
2. **绝不白屏**：加载失败 / HTTP 4xx-5xx / 平台视图不可用 → 退化为可读错误 + 「重试」+「检查服务端地址」
3. **单向深链**：页面唤起原生只能跳 `harness://`，原生拦截并白名单解析

**新增要求**：

- **入口地址构造沿用 `web_entry.dart`**（已处理 `?#` 尾巴坑，勿重写）
- 加载前必须完成认证透传（§4.2），否则会出现登录页闪烁
- 支持深链直达具体会话：`harness://session/<sid>`（为推送点开做准备）

### 4.2 认证透传（**本方案的最大技术前置**）

**问题**：原生凭据在 Keychain，WebView 的 Cookie jar 是独立的，不做交换则每次进 WebView 都要重登。

**方案对比**：

| 方案 | 做法 | 安全 | 服务端改动 | 评价 |
| --- | --- | --- | --- | --- |
| A. WebView 内重登 | 页面走正常登录 | 中 | 零 | 体验差，不推荐 |
| **B. Cookie 注入** | 原生把会话 Cookie 塞进 WebView CookieManager | 高（HttpOnly，页面 JS 读不到） | 零 | **首批落地推荐** |
| **C. 一次性 ticket** | 原生换短时 ticket → 页面用 ticket 换专属会话 | 最高（一次性 + 短 TTL） | 中（2 端点） | **目标态** |

**推荐路径**：**B 先行，C 跟进**。两者不冲突。

**方案 C 的接口（草案，与协议 §6.2 对齐）**：

```
① 签发（需用户会话）
POST /api/v1/auth/webview-ticket
Body: { device_id, ttl_s }
Resp: { ticket, expires_at }

② 传递（URL fragment，不进 Referer / 不落 access log）
https://<server>/#ticket=<ticket>

③ 兑换（唯一需新增 publicPaths 的端点）
POST /api/v1/auth/webview-exchange
Body: { ticket }
Resp: 200 + Set-Cookie: hg_sess=<短时会话>; HttpOnly; SameSite=Lax
```

**硬约束**：

- ticket 一次性消费，重放返回 401
- ticket 绝不写日志（`AccessLog` 中间件对该 path 脱敏）
- 兑换出的会话**权限降级**：仅读 + 会话内发消息，**禁止 `decideApproval`**（与协议 §8 一致）

**已经定案的前置：登录只在原生（见 §6.1 决策 2）**

```
[原生] 登录 → 拿 device_token + 用户会话
   ↓
[原生] 签发 ticket（携带 device_id）
   ↓
[WebView] 凭 ticket 换 Cookie → 进入 Web UI
```

**边界约束**：

| 场景 | 允许的处置 |
| --- | --- |
| ticket 过期 / 失效 | 退回**原生**登录页重新登录后重签，**不得**在 WebView 内弹登录表单 |
| `hg_sess` Cookie 失效 | Web UI 检测到 401 → 通过 `harness://reauth` 深链请求原生重签 ticket |
| 首次安装未登录 | 走原生登录，登录成功后才允许进入 WebView |

> **为什么禁止 WebView 内登录**：WebView 内登录拿不到 `device_token`，后续 ticket 签发、设备身份校验（协议 §5.3）、能力声明（§4.3）全部失去依据，且会在服务端产生「无法识别来源端」的会话。

### 4.3 能力声明注入（让 Web UI 知道「我在手机上」）

```js
window.harnessMobile = {
  capabilities: {
    approvalDecide: false,   // 审批只读
    createProject: false,    // 禁止建项目
    fileUpload: true,        // 允许相册上传
    exec: false              // 不执行命令
  }
}
```

**Web UI 据此**：

- 审批卡片按钮替换为「请在电脑端确认」
- 隐藏「新建项目」入口
- 保留 `<input type="file" accept="image/*">`

> ⚠️ **这不是安全边界**（可被绕过），仅用于体验降级。真正的强制在服务端（协议 §5.3）。

### 4.4 相册上传

**零新增开发**：WebView 内 `<input type="file" accept="image/*">` 在 Android/iOS 会自动调起系统相册。

**平台配置要求**：

- Android：`WebChromeClient.onShowFileChooser` 需实现，并申请相册权限
- iOS：`WKWebView` 的 `UIDelegate` 需实现 `runOpenPanelWith`，`Info.plist` 加 `NSPhotoLibraryUsageDescription`

> 这是唯一需要写原生平台通道的地方（Kotlin / Swift 各一段）。

### 4.5 推送与唤醒

- FCM / APNs 收到通知 → 点击进入 → 深链 `harness://session/<sid>` → WebView 直达该会话
- **不承诺后台实时**（R4 重述）：WebView 退后台 JS 被挂起，回前台需 Web UI 自行 `resync`

### 4.6 设备在线状态机制（**瘦身版 `device_ws` 的存在理由**）

#### 4.6.1 为什么必须保留 WS（源码依据）

```go
// internal/device/hub.go:200-206
// Online 设备当前是否在线（有有效连接）。
func (h *Hub) Online(deviceID string) bool {
    _, ok := h.conns[deviceID]   // 只看内存连接表，不看 DB、不看 last_seen_at
    return ok
}
```

**唯一入口**是 `GET /api/v1/devices/ws`（`router.go:163`）。因此：

```
无 WS 连接 → conns 无记录 → Online() 恒 false → 客户端列表永远显示离线
```

**没有第二条路。** `devices.last_seen_at` 虽然会被 `OnHeartbeat` 回调写入，但 `Online()` **完全不读它**，所以频繁的 HTTP 请求无法改变在线显示。

> 这是本方案对「删除 device_ws」决策的修正依据：`device_ws` 不只服务于端侧执行，它同时是**在线状态的载体**。移动端不执行工具，但需要被别人看见在线。

#### 4.6.2 瘦身边界

| 内容 | 处置 | 理由 |
| --- | --- | --- |
| 握手（`hello` → `welcome`） | ✅ 保留 | `welcome` 下发 `heartbeat_s` |
| **心跳 `ping`（周期上报）** | ✅ **必须保留** | 在线状态的唯一来源 |
| 退避重连（1s→2s→4s→8s→30s，±20% 抖动） | ✅ 保留 | 弱网必备 |
| 状态机（connecting / open / reconnecting / dead） | ✅ 保留 | 需处理服务端 `device.replaced` |
| `welcome.heartbeat_s * 0.8` 取值 | ✅ 保留 | 铁律：绝不硬编码 15s |
| 任务派发帧（`task.*`） | ❌ 裁剪 | 移动端不做执行 |
| 任务结果上报（含 `source_trust`） | ❌ 裁剪 | 原 R2 已重述失效 |

**规模**：480 行 → 约 **200-250 行**。`device_connection.dart`（70 行）完整保留。

#### 4.6.3 在线状态的精确语义（**必须如实告知用户**）

| 场景 | 在线状态 | 说明 |
| --- | --- | --- |
| App 在前台 | ✅ **实时在线** | WS 连接 + 周期 ping |
| App 切后台 / 锁屏 **≤45s** | ✅ 仍在线 | `OfflineAfter` 未超时 |
| App 切后台 / 锁屏 **>45s** | ❌ **离线** | `hub.go:36` `OfflineAfter` 默认 45s（3×15s 心跳） |
| App 被划掉 | ❌ 离线 | — |
| 网络切换（4G↔WiFi） | ⚠️ 短暂离线后自动恢复 | 退避重连 |

> **不追求后台常驻在线**。若要真正后台在线，需 Android 前台服务 + iOS Background Mode，会显著增加功耗与上架审核风险，**本方案明确不做**。

#### 4.6.4 对客户端列表 UI 的要求

- 显示「在线 / 离线」沿用 `Hub.Online()` 真值，不做二次推断
- 移动端离线时**不应显示为「故障」**，文案建议「移动端 · 仅对话」
- 移动端 Workspace 在 PC 切换器中的既有提示（`WorkspaceSwitcher.tsx:86`）已契合：「该工作空间离线，仅可查看历史对话」

#### 4.6.5 与对话实时性的关系（**两者独立，勿混淆**）

| 能力 | 承载通道 | 是否受 WS 影响 |
| --- | --- | --- |
| 对话流式实时性 | WebView 内浏览器直连 `GET /sessions/{sid}/runs/{rid}/events`（SSE） | ❌ **无关** |
| 设备在线状态 | 原生 `device_ws` 的 WS 连接 + 心跳 | ✅ **强依赖** |

**关键事实**：`runEvents` 走的是服务端 `Bus.Subscribe(rid, fromSeq)`，是**多订阅者**模型。客户端 A 与手机 WebView 同时订阅同一 `runID`，**看到的是同一份事件流，内容与实时性完全一致**——因为真值在服务端（协议 R1）。

两者唯一的耦合点：App 退后台时 **WS 与 SSE 会同时断**，回前台后 WS 自动重连、SSE 由 Web UI 按 `last_event_id` 续传或 `resync` 重拉快照。

### 4.7 已定案的三项能力处置

#### 4.7.1 生物识别（`local_auth`）：保留，仅用于 WebView 解锁

**处置**：`core/app/biometric_gate.dart`（45 行）**保留**，但用途彻底变更。

| 用途 | 状态 | 说明 |
| --- | --- | --- |
| 审批决策前置校验（原 `BiometricGate.authenticate`） | ❌ **移除** | 审批中心整体删除，该调用点消失 |
| **WebView 解锁** | ✅ **保留** | 冷启动 / 回前台 / 手动锁定时，要求指纹或面容后才进入 WebView |

**为什么值**：`local_auth` 已集成（`pubspec.yaml`），`BiometricGate` 的 fail-closed 语义（拿不到结果即拒绝）正是解锁场景需要的。移动端常被他人短暂接触，WebView 内含完整对话历史与配置入口，加一道本地锁成本极低。

**实现要点**：

- 锁的粒度是 **App 级**，不是审批级
- 解锁失败 **不降级为密码**（避免绕过生物识别），直接停留在锁定页
- 锁定页提供「重新验证」按钮，不提供「跳过」
- 与 §4.2 登录链路的关系：**先解锁，再检查登录态**；未登录则走原生登录（§4.2）

> ⚠️ 注意与红线的一致性：这不改变 R3（令牌仍只在 Keychain），生物识别只是**访问前置门**，不参与任何密钥派生。

#### 4.7.2 图片识别：投放页删除后不受影响

**链路等价性证明**：

| 环节 | 现方案（原生投放页） | 新方案（WebView file input） |
| --- | --- | --- |
| 选图 | `image_picker` 平台通道 | `<input type="file" accept="image/*">` |
| 体积校验 | `delivery_api.dart` 本地校验 2MB | Web UI 侧校验（或交给服务端） |
| 传输 | base64 内联进工具调用参数 | **完全相同**：base64 内联 |
| 服务端 | 无专用上传端点（只有下行 `GET /artifacts/{id}`） | **不变** |
| 模型 | 视觉模型消费 | **不变** |

**结论**：服务的端到端链路没有任何变化，只是**选图入口从未原生迁到 WebView**。删除 `delivery_page.dart`(376) / `delivery_queue.dart`(127) / `delivery_api.dart`(112) 不影响图片识别能力。

**唯一需补的平台配置**（见 §4.4）：

- Android：`WebChromeClient.onShowFileChooser` + 相册权限
- iOS：`WKWebView` 的 `UIDelegate.runOpenPanelWith` + `NSPhotoLibraryUsageDescription`

#### 4.7.3 `workspace.list`：不申报

**定案**：移动端 `capabilities` **不包含** `workspace.list`。

**为什么与「可见性」无关（已核实源码）**：

```go
// pkg/toolapi/spec.go:98-104
// CapWorkspaceList 只读列举目录（fs.list / fs.roots）。
// 与 CapWorkspaceRead 的区别是阅界更窄：只允许 readdir 级元数据，
// 绝不读文件内容；语义为「工作区宿主目录可视化选择」。
CapWorkspaceList = "workspace.list"
```

未申报时的唯一后果（`api/fs_handler.go:220`）：

```go
return "", apperr.New(apperr.CodeFSHostUnsupported,
    "该工作区暂不支持目录列举，请手动填写路径")
```

| 关注点 | 是否受 `workspace.list` 影响 |
| --- | --- |
| 出现在客户端列表 | ❌ 不由它决定（看 `devices` 表配对记录） |
| 显示在线/离线 | ❌ 不由它决定（看 `Hub.Online()`，见 §4.6.1） |
| 出现在工作空间列表 | ❌ 不由它决定（看配对后自动建 Workspace） |
| **目录选择器可用性** | ✅ **唯一受它控制** |

**结论**：不申报只意味着「在手机上不能点选目录，需要手填路径」，**不会让移动端从客户端列表消失**。

**为什么不申报更好**：移动端不建项目、不选工作区目录（协议 §5.3 强制 `workspace_id ∈ {空, mobile}`），申报该能力只会扩大攻击面而无收益。

## 6. 决策项

### 6.1 已定案（本版关闭）

| # | 问题 | 定案 | 影响的章节 |
| --- | --- | --- | --- |
| 1 | `device_ws.dart`（480 行）是否保留？ | ✅ **保留但瘦身**（→ 约 200-250 行）。理由：`Hub.Online()` 只看内存连接表——**没有 WS 连接就没有在线状态**，这是在线状态唯一来源，WebView 内浏览器无法替代原生维持设备 WS。裁剪项：任务派发帧、任务结果上报；保留项：握手、心跳 ping、退避重连、状态机 | §3.2 / §4.6 / §7 M7 |
| 1b | `device_connection.dart`（70 行）是否保留？ | ✅ **保留**。与 `device_ws` 同生命周期，不可分离 | §3.2 |
| 2 | 登录放原生还是 WebView 内？ | ✅ **原生登录**。理由：只有原生登录才能拿到 `device_token`，而它是签发 WebView ticket 的前提；WebView 内登录无法获得设备身份，会导致 §4.3 的能力声明与协议 §5.3 的端侧校验失去依据 | §3.2 / §4.2 |

> **决策 2 的连带约束**：WebView **不得**提供登录入口。若 ticket / Cookie 透传失败，应退回原生登录页重新登录，而不是让用户在 WebView 里输入密码（否则会绕过 `device_token` 链路）。

## 7. 分批实施计划

| 批次 | 内容 | 前置 | 风险 |
| --- | --- | --- | --- |
| **M0** | 原生登录链路确认（**已定案：登录只在原生**）+ 配对上报 `kind=mobile` 验证 + WebView 免登方案 B（Cookie 注入） | 服务端 D2 | 低 |
| **M1** | WebView 主体化：入口、深链、错误态、能力声明注入（**不含登录入口**） | M0 + D5 | 中 |
| **M2** | 删除审批模块（approval/* + approval_api + approval_repository + biometric 决策用法） | 无 | 低（纯删） |
| **M3** | 删除会话只读页与 SSE 客户端 | M1 可用 | 低（纯删） |
| **M4** | 删除投递模块，改用 file input + 平台通道 | M1 可用 | 中（需写 Kotlin/Swift） |
| **M5** | 推送深链直达会话 | M1 | 中 |
| **M6** | 切换方案 C（一次性 ticket），移除 Cookie 注入 | 服务端 D4 | 中 |
| **M7** | `device_ws` 瘦身：裁剪任务派发/结果上报，保留握手/心跳/退避/状态机（**已定案：保留瘦身，不删除**） | M3 | 中 |

> **排序原则**：先立新（M0-M1 保证可用），再拆旧（M2-M7）。**不允许先删后建**——那会让中间态完全不可用。
>
> **M7 为何排在 M3 之后**：`device_ws` 承担在线状态与配对保活，瘦身必须在 WebView（M1）确认能独立承担对话实时性之后进行，避免出现「配对成功但收不到任何状态」的空窗。**注意 M7 是「裁剪」不是「删除」**——连接层与心跳必须保留。

## 8. 风险与已知限制

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | **WebView 退后台 JS 挂起** | 回前台看到过期状态 | Web UI 已有 `active-run` 重建机制；需真机验证 iOS 侧表现 |

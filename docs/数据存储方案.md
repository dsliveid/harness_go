# harness_go 数据存储方案（定稿 v2.0 · 分库版）

| 项目 | 内容 |
| --- | --- |
| 版本 | **v2.0**（v1.0 单库版 → v2.0 **按会话分库** + 会话级 blob 分包；用户 2026-11 决策） |
| 依据 | 桌面端 `harness_mini` 实测（`store.rs` + `.dev-data/` 目录）；本项目 `架构设计文档.md` §7 |
| 核心结论 | **可行**。采用「**主库（跨会话）+ 每会话一库（会话域）+ 会话级 blob 分包**」；但必须同时落实 **连接池 + 惰性迁移 + 主库摘要冗余** 三项配套，否则长会话场景下会失控 |
| 影响作业包 | A-3（store）拆为 `store/main` + `store/session` 双库 + `SessionStore` 路由与 LRU 池；阶段 G 快照仍走**全局** CAS |

---

## 0. 结论（先说可行性与代价）

**判定：可行，且对你的场景（长对话为主、跨会话统计少）比单库更优。** 理由与代价如下：

| 维度 | 分库（本方案） | 单库（v1.0） |
| --- | --- | --- |
| 长对话隔离 | ✅ 单会话 messages 10 万行不影响其他会话 | ❌ 全库一起变慢，VACUUM 需停机 |
| 删除会话 | ✅ O(1) 删目录 | ❌ 级联删数万行 + 碎片 + VACUUM |
| 损坏隔离 | ✅ 单库损坏不波及其他会话 | ❌ 全库一起不可用 |
| 会话导出/迁移 | ✅ 直接打包目录（自带 db + blob） | ⚠️ 需按行导出 + 收集 blob |
| 会话列表/统计 | ⚠️ 需主库**冗余摘要列** | ✅ 直接 JOIN |
| 跨会话全文搜索 | ⚠️ 需主库另建 FTS 索引（阶段 D） | ✅ 直接查 |
| 备份原子性 | ⚠️ 多文件，无法一次原子快照 | ✅ 单文件 `VACUUM INTO` |
| 工程复杂度 | ⚠️ 连接池 + 懒迁移 + 表归属契约 | ✅ 低 |

**三项必须配套的工程措施（缺一项就会翻车）**：

1. **`SessionStore` 路由 + LRU 连接池**：每个打开的会话占 1 个 SQLite 连接，必须限制同时打开数（默认 8，可配），闲置超时关闭。否则 500 个会话 = 500 个句柄。
2. **惰性建库 + 惰性迁移**：空会话**不建库文件**（首次写消息才建）；打开会话时检查 `schema_version`，落后则就地迁移。启动时只迁移主库，绝不全量扫所有会话库。
3. **主库摘要冗余列**：`sessions` 表冗余 `message_count` / `last_message_at` / `total_tokens` / `last_run_status`，写消息时同步更新（**非事务、最终一致**）。会话列表与统计只读主库，永不跨库扫描。

> **兜底后路**：`store` 层抽象出 `SessionRepo` 接口，`main` 与 `session` 两种物理实现都满足同一接口。若将来发现分库弊大于利，可切回单库实现而不动 `agent`/`service`/`api` 任何代码。这条在 A-3 就要留好。

## 1. 桌面端实测（参照基线）

```
harness_mini/.dev-data/
  harness_mini.db        212 MB    ← 关系数据单库（未分库，长会话已明显膨胀）
  secret.key  daemon.json
  sessions/<sid>/artifacts/blobs/<xx>/<hash>   ← 会话产物 CAS（会话级分包）
  snapshots/blobs/<sha256>                     ← 文件快照 CAS（**全局**）
  attachments/<sid>/<hash>_image.png           ← 附件按会话分包
  clones/ worktrees/ temp-project/             ← 临时空间（**web 版已取消，不建这些目录**）
harness_mini/.harness/  memory/ plans/ skills/ ...
```

`store.rs` 关键事实：PRAGMA `WAL / busy_timeout=5000 / synchronous=NORMAL / auto_vacuum=INCREMENTAL / foreign_keys=ON`；附件走 `attachments_json` + 按会话目录文件；工具输出 `sanitize_overflow_text` 截断入库；**迁移用 `ensure_column()` 运行时补列（40+ 处，重债，不采纳）**。

**注意**：桌面端在文件层已经是「**会话级分包**」（sessions/、attachments/），但关系库仍是单库。本方案把分包**再往前推一步到数据库层**——这正是你想要的。

## 2. 定稿架构

### 2.1 目录布局

```
data/
  main.db  main.db-wal  main.db-shm          # 主库：跨会话共享数据
  secret.key                                  # 主密钥 0600
  initial_password                            # 首启口令 0600
  app.log
  sessions/
    <sid>/
      session.db  session.db-wal  session.db-shm   # 会话库（懒建）
      blobs/<xx>/<sha256>                          # 会话级 CAS（附件/产物/大工具输出）
      bundle/                                      # 会话导出包（阶段 G）
  snapshots/blobs/<sha256>                     # 全局 CAS（文件快照，跨会话去重）
  tmp/                                         # blob 原子写暂存（须与目标同盘）
  tokenizers/   run/
```

> **临时空间已取消**（2026-11）：不建 `clones/` / `worktrees/` / `temp-project/`，不做 git 沙箱；工作区根固定为项目级。

### 2.2 表归属划分（**核心契约，定错则后面返工**）

| 表 | 位置 | 理由 |
| --- | --- | --- |
| `sessions` | **主库** | 跨会话列表/排序/搜索；含摘要冗余列 |
| `users` / `api_tokens` / `providers` / `settings` | **主库** | 全局共享 |
| `devices` / `session_leases`（阶段 C） | **主库** | 跨端可见 |
| `tool_packages`（阶段 E） | **主库** | 全局安装态 |
| `schema_migrations` | **主库 + 每会话库各一份** | 两套独立版本 |
| `messages` | **会话库** | 量最大（长对话主体） |
| `runs` | **会话库** | 与会话消息同事务 |
| `tool_events` | **会话库** | 会话域审计 |
| `approvals` | **会话库** | 审批属会话域 |
| `approval_rules` | **会话库** | 「本会话允许」天然会话级（去掉 `session_id` 列） |
| `blobs`（索引） | **会话库** | 只索引本会话目录下的 blob |
| `session_meta`（单行） | **会话库** | `session_id / created_at / schema_version`，使会话库**自包含**可独立打开与导出 |

> 会话库内不再有 `sessions` 表（避免与主库外键冲突）；会话标题等可变字段以主库为准，导出时由 bundle 写入 `session_meta` 快照。

### 2.3 会话库生命周期

| 阶段 | 行为 |
| --- | --- |
| 新建会话 | **只在主库插 `sessions` 行，不建库文件**（避免空库污染） |
| 首次写消息 | 创建 `sessions/<sid>/session.db` → 跑 `0001_init.sql`（会话库版）→ 写入 |
| 打开会话 | 路由取连接：池中命中 → 复用；未命中 → 打开 + 校验 `schema_version`（落后则**就地迁移**）+ 入池 |
| 闲置 | LRU 超上限或闲置 >10min → `wal_checkpoint(TRUNCATE)` 后关连接、出池 |
| 删除会话 | ①主库删 `sessions` 行 ②删 `sessions/<sid>/` 整目录。①成功②失败 → 留孤儿目录，启动时清理 |
| 启动 | **只迁移主库**；扫描孤儿会话目录（无主库行）与孤儿主库行（无目录，仅告警不自动删） |

### 2.4 主库摘要冗余（统计的唯一数据源）

```sql
-- 主库 sessions 表追加列
message_count     INTEGER NOT NULL DEFAULT 0,   -- 写消息时 +1
last_message_at   INTEGER,
total_tokens      INTEGER NOT NULL DEFAULT 0,   -- runs 结束时累加
last_run_status   TEXT,                          -- completed/failed/…（会话列表徽标）
```

更新时机：消息落库后、Run 状态迁移后，各发一次主库 UPDATE（**不与会话库同事务**）。失败只影响列表展示的新鲜度，不影响对话正确性 —— 这是**有意接受的最终一致**。

> 列表页只读主库；如需精确消息数，可在打开会话时用会话库 `COUNT(*)` 校正一次。

## 3. blobs：会话级分包（按你的要求），快照例外走全局

| 对象 | 位置 | 去重 | 理由 |
| --- | --- | --- | --- |
| 附件 / 图片 / 会话产物 / 大工具输出 | `sessions/<sid>/blobs/<xx>/<sha256>` | **会话内去重**（同会话重复上传只存一份） | 删会话即回收，无孤儿、无全局 GC |
| 文件快照（阶段 G） | `snapshots/blobs/<sha256>`（**全局**） | **全局去重 + ref_count** | 同一文件版本被多个会话改过时只存一份；桌面端也这么做 |

**为什么快照要全局**：快照是「文件内容版本」，同一份 `main.go@v3` 可能在 10 个会话里都出现；会话级存储会存 10 份。而附件是「用户上传的一次性素材」，跨会话复用概率低。这条划分与桌面端实测一致。

**会话内 blob 写入**（同样 tmp→rename 原子写，同盘）：
```
data/tmp/<uuid>.part → fsync → rename 到 data/sessions/<sid>/blobs/<xx>/<hash>
→ 会话库同事务 INSERT OR IGNORE blobs(hash,size,mime) （**无 ref_count**，会话内一律视为被引用）
```
- 会话库的 `blobs` 表**不需要 `ref_count`**：会话级目录随会话整体删除，不做细粒度回收。
- 全局快照 CAS 保留 `ref_count` + GC（阶段 G 实现，A 阶段只需留好端口）。

### 3.1 阈值（上限调至 64MB）

| 对象 | 阈值 | 超限处理 |
| --- | --- | --- |
| 单 blob 上限 | **64 MB**（`storage.max_blob_mb`，默认 64） | 拒绝并返回 `storage.blob_too_large` |
| 附件 / 图片 | 一律走 CAS | 二进制不进 DB |
| 消息正文 | >32 KB | 转 blob，`content` 存 `blobref:<hash>` + 前 2000 字摘要 |
| 工具结果 | >16 KB | `result_json` 存摘要 + `result_blob` 记 hash |
| 前端上传 | 64 MB（与后端一致） | UI 侧提前拦截并提示 |

> 64MB 已足够覆盖长日志、大图片、模型大输出；同时把 `data` 目录配额告警阈值从 2GB 提到 **8GB**（按会话分包后总容量会更大）。

### 3.2 可读资产文件化（不受分库影响，仍是独立一层）

| 资产 | 位置 | 写入方 | DB 索引 |
| --- | --- | --- | --- |
| 项目记忆 | `<ws>/.harness/memory/*.md` | `memory` 插件（阶段 F） | 阶段 D 起 FTS5/向量（派生，可重建） |
| 计划文档 | `<ws>/.harness/plans/*.md` | `plan` 插件（阶段 F） | 否（扫目录） |
| 技能 | `<ws>/.harness/skills/<name>/` | `skill` 插件（阶段 F） | 阶段 D 索引 |
| SOP | `<ws>/.harness/sop/*.md` | `sop` 插件（阶段 G） | 阶段 D 索引 |
| 子任务 | `<ws>/.harness/subtasks/` | `subagent`（阶段 F） | 否 |

原则：**文件是唯一真源，DB 索引是可重建的派生数据**（`harness-go reindex`，阶段 D）。项目级资产跟随工作区，与会话库的"按会话分库"互不影响。

## 4. 零跨库事务（设计约束，必须守住）

SQLite 的多库原子提交（super-journal）只在 rollback journal 模式下可靠，**WAL 下不保证**。因此本方案从设计上**消除所有跨库事务需求**：

| 写路径 | 涉及库 | 是否同事务 | 说明 |
| --- | --- | --- | --- |
| 发消息（user message + run pending） | 会话库 | ✅ 同库事务 | 天然满足 |
| 工具调用（tool_events + approvals） | 会话库 | ✅ 同库事务 | 天然满足 |
| Run 状态迁移（runs + 摘要回写） | 会话库 + 主库 | ❌ 分两步 | 摘要回写失败可重试，不影响正确性 |
| 新建会话 | 主库（仅插行） | ✅ | 不建会话库文件 |
| 删除会话 | 主库删行 + 删目录 | ❌ 分两步 | 先删行后删目录，孤儿由启动清理 |
| 审批规则 | 会话库 | ✅ | — |
| 会话列表/统计 | 主库只读 | — | 不跨库 |

**禁止事项（代码评审必查）**：
- ❌ 在同一个事务里同时写主库与会话库
- ❌ 用 `ATTACH` 把会话库挂到主库连接上做联表查询（会引入跨库锁与不一致）
- ❌ 会话列表/统计去扫描会话库（必须只读主库摘要列）
- ❌ 在主库里对 `sessions.id` 建外键指向会话库数据

## 5. 迁移策略

| 库 | 迁移时机 | 说明 |
| --- | --- | --- |
| 主库 | 启动时 | 必须成功，失败即拒绝启动（打印备份路径与失败版本） |
| 会话库 | **打开该会话时惰性执行** | 启动不扫全量；后台任务访问旧库前也必须先迁移 |
| 版本表 | 各自 `schema_migrations` | 两套独立版本线（`main/0001…`、`session/0001…`） |
| 迁移文件 | `internal/store/migrations/main/*.sql`、`.../session/*.sql` | embed，**已发布永不修改** |
| 破坏性变更 | 新表 + 搬迁 + 改名，同一迁移内完成 | 不做自动回滚 |

**明确不采纳桌面端做法**：运行时 `ensure_column()` 逐列探测补列（40+ 处 + 大量 `legacy_*` 测试）。禁止在 Go 代码里拼 DDL（测试用临时库除外）。

## 6. 并发与连接管理

| 项 | 约定 |
| --- | --- |
| 主库 | 1 写连接（`SetMaxOpenConns(1)`）+ 读连接池；WAL 允许并发读 |
| 会话库 | 每库 1 写连接；**同一时刻只有 lease holder 可写**（A 阶段即 per-session mutex，C 阶段升级为跨端租约） |
| 连接池 | LRU，默认上限 **8** 个会话库同时打开（`storage.max_open_sessions`），可配；超限淘汰最久未用（先 checkpoint 再关） |
| 句柄预算 | 1 主库 + 8 会话库 ≈ 9 个 SQLite 连接，内存占用可控（每库页缓存默认 2MB → 约 20MB） |
| WAL 文件 | 会话库关闭前 `wal_checkpoint(TRUNCATE)`，避免 5000 个会话产生 15000 个 `-wal/-shm` 残留文件 |

## 7. 备份、导出与多端

| 场景 | 方案 |
| --- | --- |
| 整机备份 | 主库 `VACUUM INTO` + `sessions/` 目录整体复制；**先停写**（优雅关闭后备份最稳） |
| 单会话导出（阶段 G） | 打包 `sessions/<sid>/`（`session.db` + `blobs/`）+ `manifest.json`（schema 版本、主库摘要快照）→ zip |
| 单会话导入 | 校验 manifest → 解压到新 `<sid>` → 主库插 `sessions` 行 → 惰性迁移到当前 schema |
| 跨版本恢复 | 旧 bundle 导入后按当前 schema 迁移会话库 |
| 多端下发（C/E） | 工具包/技能包 = zip + manifest + 签名，复用同一打包器 |

> 分库的额外好处：**单会话导出天然自包含**，不需要"按行收集 + 收集 blob 引用"。

## 8. 维护与容量治理

| 操作 | 时机 | 说明 |
| --- | --- | --- |
| `wal_checkpoint(TRUNCATE)` | 会话库出池 / 优雅关闭 | 收缩 WAL，减少残留文件 |
| `incremental_vacuum` | 每周 / 手动 | 主库 + 各会话库（**按需遍历，不阻塞**） |
| `VACUUM` | 手动 / 单库增长 >30% | 单会话库可独立 VACUUM，**不影响其他会话**（分库最大收益之一） |
| 统计 | `/api/v1/settings/maintenance` | 主库页数/freelist + 会话库总数/总字节/最大会话 |
| 孤儿清理 | 启动时 | 无主库行的会话目录、无目录的主库行（仅告警） |
| 配额告警 | `data` > 8GB | 日志 + UI 提示，不硬性阻断 |

## 9. 风险登记表与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | 会话库数量膨胀（数千个）导致句柄/文件数压力 | 高 | LRU 连接池上限 8；空会话不建库；出池 checkpoint；Windows 上关注杀软扫描（`data/` 建议加排除） |
| R2 | 跨会话统计变慢 | 中 | 主库摘要冗余列（§2.4），列表/统计只读主库 |
| R3 | 跨会话全文搜索缺失 | 中 | 阶段 D 在主库建 FTS5 索引（写入时从会话库同步）；A 阶段先支持"当前会话内搜索" |
| R4 | 备份无法原子 | 中 | 优雅关闭后备份；提供 `backup` 命令串行执行（主库 → 各会话库） |
| R5 | 会话库 schema 漂移（用户长期不开某会话） | 中 | 惰性迁移 + 打开即迁移；`maintenance` 提供"批量迁移"手动项 |
| R6 | 误用跨库事务/ATTACH 联查 | 高 | §4 禁止清单 + 代码评审 + store 层不暴露 `*sql.DB` 给上层（只暴露仓储方法） |
| R7 | 摘要列与实际不一致 | 低 | 打开会话时校正；提供 `reconcile` 维护命令 |
| R8 | 分库后发现弊大于利 | 中 | `SessionRepo` 接口抽象，可切回单库实现（§0 兜底后路） |

## 11. 验收清单（A-3 出口）

1. 空目录启动 → 建 `data/main.db`（WAL、`integrity_check` 通过），**不建任何会话库**。
2. 新建会话 → 主库 1 行，**无库文件**；发首条消息 → 才出现 `sessions/<sid>/session.db`。
3. 同一附件在同一会话内上传 2 次 → 磁盘仅 1 份；不同会话各 1 份（符合"按原本方式"）。
4. 打开 20 个会话 → 同时打开连接数 ≤ `max_open_sessions`(8)，其余被 LRU 淘汰并已 checkpoint。
5. 会话列表 100 条 → **只读主库**（SQL 日志断言无会话库访问）。
6. 会话库 `schema_version` 落后 → 打开时自动迁移；重复打开幂等。
7. 删除会话 → 主库行与目录均消失；人为只删主库行 → 重启后孤儿目录被清理。
8. 写 blob 中途 kill → 重启无半写 `.part`，会话库无脏引用。
9. 单个 64MB blob 可写入；65MB 被拒并返回 `storage.blob_too_large`。
10. 单会话库 `VACUUM` 期间其他会话读写正常（分库收益验证）。
11. 代码评审：全仓无 `ATTACH`、无跨库事务、`store` 不向上暴露 `*sql.DB`。

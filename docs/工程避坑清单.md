# harness_go 工程避坑清单（源自桌面版实战教训）

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v0.1 |
| 来源 | `harness_mini` 的 60+ 篇治理规范（均为真实事故复盘，非理论推演） |
| 用途 | ① M0–M3 实现期的 checklist；② Code Review 必查项；③ 测试用例设计依据 |
| 使用方式 | 每条含「现象 → 根因 → web 版必须实现的细节 → 验收方式」，实现时逐条对照 |

> 标注说明：`[高危]` = 会导致白屏/数据错乱/卡死，必须在一期解决；`[中]` = 影响体验或可维护性，一期尽量解决。

## 0. Top 10 必踩坑（按 web 版踩中概率排序）

| # | 坑 | 一句话结论 |
| --- | --- | --- |
| 1 | 消息分页与合并顺序错乱 `[高危]` | 分页必须按**轮次**切，合并必须按 `seq` 重排，禁止"本地多出来的就追加到末尾" |
| 2 | Zustand 选择器返回新引用 `[高危]` | `?? []`、`[...arr].sort()` 会造成渲染风暴甚至无限请求循环 |
| 3 | React Hooks 条件早退 `[高危]` | 组件白屏，必须 lint 强制 + 按消息粒度 ErrorBoundary |
| 4 | 上下文前缀缓存被击穿 `[高危]` | 动态内容放 system prompt 开头 = 每轮缓存 0 命中，首 token 从 2s 变 30s |
| 5 | 用正文关键字判断运行状态 `[高危]` | `content.includes("⚠️")` 会把正常交付误判为崩溃 |
| 6 | 压缩切断 tool_call 配对 `[高危]` | 孤立 tool 消息 → 上游 400，必须按"轮次原子淘汰" |
| 7 | 流式高频落库抢 SQLite 锁 `[高危]` | 流式中每 800ms 写库会让设置保存、会话切换全部卡死 |
| 8 | 重试未清理后续消息 `[高危]` | 历史以 assistant 结尾 → 模型返回空字符串 |
| 9 | 重启遗留 running 状态 `[高危]` | 界面无限转圈，必须启动时统一置 interrupted |
| 10 | 全局设置对象被组件整体订阅 `[中]` | 一次保存设置导致上百张工具卡片同时重渲染 |

## A. 前端渲染与状态

### A1. React Hooks 条件早退导致整窗白屏 `[高危，已踩中并修复]`

- **现象**：长会话中流式输出或展开工具卡片时窗口瞬间白屏，报 `Rendered more hooks than during the previous render`。
- **根因**：组件内在 Hook 之间写了 `if (!props) return null`。React 的 Hook 以链表存储，两次渲染 Hook 数量不一致即触发不可恢复异常，只能由最外层 ErrorBoundary 兜底。
- **本仓库真实案例（2026-11 实测）**：`web/src/features/chat/SideRail.tsx` 在 `if (!hasItems) return null`（第 59 行）**之后**声明了 `const activePointerRef = useRef(...)`（原第 62 行）。`hasItems` 由 `todos / activePlan / commands / subagents` 派生：
  - 会话为空 → `hasItems=false` → 本次渲染只跑 4 个 Hook 就 return；
  - 工具跑起来 → `hasItems=true` → 变成 5 个 Hook → 抛 `Minified React error #310` → **整棵树崩塌为黑屏**。

  该缺陷的隐蔽性在于**时机依赖派生数据**：静止页面完全正常，一旦有工具在跑就黑屏，容易被误判成「后端/流式的问题」。现已把 ref 上提到 Hook 区并留防复发注释。
- **web 版必须实现**：
  1. ESLint `react-hooks/rules-of-hooks` 设为 **error**（CI 阻断），`exhaustive-deps` 设 warn；
  2. **所有 Hook 必须在任何 return 之前调用完毕**，条件渲染放在 Hook 之后；
  3. ErrorBoundary **按消息粒度**包裹（每条消息一个），单条消息渲染失败降级为「原文 + 重试」，绝不整窗白屏；
  4. 顶层 ErrorBoundary 只做最后兜底，并提供「导出会话 / 重载」出口。
- **验收**：故意在消息组件里抛错，断言只有该条消息降级、其余消息与输入框正常可用。
- **静态自查**（本项目未接 ESLint 时的兜底手段）：扫描每个组件，若 `if (...) return null` 之后仍有 `useState/useRef/useEffect/useMemo/useCallback/useReducer/useContext`，即命中本坑。

### A2. Zustand 选择器返回不稳定引用导致渲染风暴 / 无限请求 `[高危]`

- **现象**：修改任意设置后 UI 卡死、内存暴涨（桌面版达 1.65GB）、CPU 打满。
- **根因**：`useStore(s => s.items[id] ?? [])` 每次求值都新建空数组；`useMemo` 里新建 `Set`；`useCallback` 依赖该 Set；`useEffect` 依赖该 callback → 无限循环请求。
- **web 版必须实现**：
  1. 空值统一用**模块级常量**：`const EMPTY: Message[] = []`，选择器返回 `s.items[id] ?? EMPTY`；
  2. 派生数据（排序、分组、Set）用 `useMemo` 且**输入必须是稳定引用**；必要时用 `useShallow` 做浅比较；
  3. **禁止**在选择器里做 `map/filter/sort`（会返回新引用）；派生放到组件内 `useMemo` 或 store 的 getter；
  4. 订阅粒度到字段：`s => s.settings.model` 而非 `s => s.settings`；
  5. 列表项组件用 `React.memo` + 稳定 key（用消息 id，不用 index）。
- **验收**：React DevTools Profiler 录制「保存设置」操作，断言重渲染组件数 < 5；连续操作 1 分钟无请求风暴。

### A3. 流式事件洪泛拖垮渲染 `[高危]`

- **现象**：桌面版对应 WebView2 消息队列 10000 条上限被打满（`0x80070718 配额不足`）。
- **根因**：每个 token 一次 IPC/一次 setState；事件生产速率远大于消费速率。
- **web 版必须实现**：
  1. delta 写入 `ref` 缓冲，**按 ~50ms 或 200 字符批量提交**到 store（一次 setState 一批）；
  2. 同一条消息的连续 delta 在服务端可选合并（> 20ms 内的 delta 合并成一个事件）；
  3. 工具输出（命令日志）单独限流：每秒最多 10 次 UI 更新，且只渲染尾部 N 行；
  4. 长列表虚拟化（只渲染可视区 ± 一屏）；
  5. 慢消费者保护（服务端）：订阅 channel 满即断开，绝不为慢客户端保留事件。
- **验收**：单次 5000 token 流式输出，主线程无 > 100ms 长任务；Performance 面板帧率 ≥ 50fps。

### A4. 事件/请求的 useEffect 依赖链失控 `[高危]`

- **现象**：某面板每秒发起上千次请求。
- **根因**：`useEffect(() => { fetch() }, [fetch])`，而 `fetch` 是依赖不稳定引用的 `useCallback`。
- **web 版必须实现**：所有数据拉取用「显式触发 + 参数快照」模式；`useEffect` 依赖数组只放原始值（id、string、number）；请求函数用 `useRef` 持有或定义在 effect 内部；带 AbortController 取消。
- **验收**：Network 面板观察任意面板 10 秒内请求数恒定。

## B. 消息序列与时间线

### B1. 分页尺寸与单轮超长消息倒挂 `[高危]`

- **现象**：最后一轮对话被显示到会话最顶部；前几轮回复混进最后一轮的执行抽屉；单轮被腰斩。
- **根因**：首屏按「最近 30 条消息」分页，而桌面版实测**单轮对话可达 60 条物理消息**（25 次 ReAct 循环）。`seq 29`（本轮 user）不在首屏 30 条内 → 后半段成为无主孤岛；再叠加合并顺序错误，渲染状态机把整段错位。
- **web 版必须实现**：
  1. **分页单位是「轮次（turn）」不是「消息条数」**：以 `run_id` 或 user 消息为边界，首屏加载「最近 N 轮」（N=3~5）的完整消息；
  2. 向后翻页同样按轮次：`?before_turn_seq=` 而非 `?before_message_seq=`；
  3. 后端提供 `GET /sessions/{id}/turns?limit=` 或消息接口支持 `turn_seq` 游标；
  4. 单轮消息数上限保护（如 200 条），超出时该轮内部再折叠执行过程（不影响 turn 边界）。
- **验收**：构造「1 轮 80 条消息 + 前面 5 轮」的会话，刷新后断言最后一轮的 user 消息与其执行过程在同一卡片内、顺序正确。

### B2. 合并消息时"本地多出来的追加到末尾" `[高危]`

- **现象**：切换会话/重连后，最新 30 条被搬到数组最前，历史被扔到末尾。
- **根因**：`mergeSessionMessages` 假设"local 有而 fetched 没有的 = 正在流式的新消息"，实际是**更早的历史**。
- **web 版必须实现**：
  1. 合并唯一算法：`Map<id, msg>` 合并 → **按 `seq` 升序排序** → 输出；
  2. 流式未落库消息用临时 id（`tmp-<uuid>`）并标记 `pending`，**落库后用服务端 id + seq 替换**，不参与 seq 排序竞争；
  3. 禁止任何"追加到末尾/开头"的隐式顺序假设，顺序只由 `seq` 决定。
- **验收**：单测覆盖「local 有历史 + fetched 只有最新一页」「local 有流式临时消息」两种合并，断言输出严格按 seq 升序。

### B3. 前端自行排序/分组导致时间线错乱 `[中]`

- **根因**：渲染层用线性扫描状态机按"遇到 user 就 flush"分组，一旦数组顺序错乱即整体错位。
- **web 版必须实现**：分组前先 `assertSortedBySeq`（dev 环境断言，生产静默修正）；分组函数为**纯函数**，输入有序数组，输出 turn 列表，单测覆盖空/单轮/多轮/中断轮。

## C. 上下文与 LLM 调用

### C1. 前缀缓存被动态内容击穿 `[高危]`

- **现象**：新一轮对话首步耗时 31.7s、缓存命中 0%；后续步骤降到 2.6s、命中 93%+。
- **根因**：① system prompt 根节点混入「计划进度/知识碎记」等高频变化内容 → Token 0 处就分支断裂；② 跨轮次事后改写历史工具消息（把上一轮工具输出替换成占位符）→ 在中途再次击穿。
- **web 版必须实现**（四层不可变上下文）：
  | 层 | 内容 | 可变性 |
  | --- | --- | --- |
  | L1 静态基座 | 角色、核心原则、工具契约 | 会话生命周期内 **100% 不变** |
  | L2 项目基线 | 项目约束、架构档案 | 低频只读 |
  | L3 历史日志 | 历史 user/assistant/tool 消息 | **append-only，入库即定型，永不改写** |
  | L4 尾部瞬态 | 最新用户输入、当前计划摘要、断点标记 | 只在最末尾变动 |
- **铁律**：动态状态一律沉到尾部锚点；**禁止跨轮改写历史消息内容**（需要瘦身时改为"新增一条 system 说明"或压缩整轮替换，而非原地改字符）。
- **验收**：连续 3 轮对话，断言第 2、3 轮首步的 `cached_tokens > 0` 且命中率 > 80%。

### C2. 上下文压缩切断 tool_call 配对 `[高危]`

- **现象**：上游返回 `400 Bad Request: An assistant message with 'tool_calls' must be followed by tool messages`。
- **根因**：按"从前往后逐条丢弃"裁剪历史，把 assistant(tool_calls) 与对应 tool 结果拆散。
- **web 版必须实现**：
  1. 裁剪单位是**完整轮次**（user → assistant(tool_calls) → tool* → assistant 整体移除）；
  2. 发送前做**序列合法性校验**：每个 `tool_calls[i].id` 必须有对应 `role=tool` 消息；不合法则拒绝发送并记录 `STORE_/PROMPT_` 错误码（不要静默发出去）；
  3. 工具结果超长时，**保留结构与首尾摘要**（如 `[前 2000 字]…[后 500 字]，完整内容见 tool_event xxx`），不要整条删；
  4. 压缩后必须重算 token 预算，并 emit `context.compacted` 事件让 UI 显示。
- **验收**：单测构造含 3 组 tool_calls 的会话，压缩后断言无孤立 tool 消息、配对完整。

### C3. token 预算低估 `[高危]`

- **见需求文档 §7.5 / 架构文档 §7.5.5**：桌面版无 tokenizer、`tools` schema 未计入预算。web 版必须走 tokenizer 注册表 + `CountChatRequest` 含 tools 全额 + usage 回填校准。

### C4. 请求报文无审计，问题无法定位 `[中]`

- **根因**：事后用 messages 表反向拼装无法还原（动态裁剪、瞬态注入、配置漂移都会失真）。
- **web 版必须实现**：
  1. 独立 `llm_requests` 审计表：`run_id / step / model / system / messages_json / tools_json / params_json / raw_usage_json / created_at`；
  2. **与 messages 物理隔离**，上下文组装器**只读 messages 业务列**，绝不消费审计表（否则 token 指数暴涨）；
  3. 写快照在发请求前完成（<1ms，WAL），不阻塞首 token；
  4. UI 懒加载（点开才拉全量 JSON），列表只返回摘要字段。
- **验收**：审计表存在时，组装上下文的 token 数与无审计表时完全一致。

### C5. 模型输出 JSON 带 Markdown 栅栏导致解析失败 `[中]`

- **根因**：模型输出 ```json … ``` 或多余开场白。
- **web 版必须实现**：结构化输出统一走「去栅栏 → 定位首个 `{` 到匹配 `}` → 解析 → 失败则降级为纯文本处理」的容错解析器，禁止直接 `json.Unmarshal` 后 panic。

## D. 生命周期与恢复

### D1. 重启遗留 `running` 脏状态 `[高危]`

- **现象**：冷启动后界面无限转圈，Run 永远"运行中"。
- **web 版必须实现**：启动时扫描 `runs.status IN ('pending','running','waiting_approval')` → 全部置 `interrupted` + `stop_reason='process_restart'` + emit 事件；前端收到 `interrupted` 展示「已中断，可重试」，**不显示加载动画**。
- **验收**：kill -9 进程后重启，断言所有 Run 终态、UI 无转圈。

### D2. 孤儿进程与端口占用 `[高危]`

- **根因**：主进程崩溃后子进程（npm run dev、编译进程）继续存活。
- **web 版必须实现**：Unix `Setpgid` + `syscall.Kill(-pid)`；Windows `CreateJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；进程退出/超时/取消三条路径都走同一个 kill 函数；启动时可选清理遗留子进程（记录 pid + 启动时间戳校验，避免误杀）。
- **验收**：启动一个 60s 睡眠命令后取消 Run，断言进程树无残留。

### D3. 重试未清理后续消息导致空回复 `[高危]`

- **现象**：点「重新执行本轮」偶发"模型返回空回复"。
- **根因**：只把指针移到最后一条 user，未清理其后的 assistant/tool 碎片；模型看到以 assistant 结尾的历史，判定已答完。
- **web 版必须实现**：重试 = ① 事务内软删（`deleted_at`）该 user 之后所有消息与 tool_events；② 新建 Run（不复用旧 Run）；③ 校验历史最后一条必须是 user；④ 前端同步清空本地占位消息。
- **验收**：单测断言重试后发送的 messages 最后一条 `role=user`。

### D4. 审批/等待通道泄漏 `[中]`

- **根因**：桌面版 `oneshot::Receiver` 只能消费一次，跨轮复用导致 panic；旧通道未清理导致"幽灵事件劫持"。
- **web 版必须实现**：每次审批生成唯一 `approval_id`，`map[approvalID]chan Decision`；决策/超时/ctx 取消三条路径都 `delete` 并从 map 移除；**同一 approval 只允许一次决策**（重复 POST 返回 409）。
- **验收**：同一审批并发 POST 两次，断言一次成功一次 409，无 goroutine 泄漏。

## E. 并发与设置

### E1. 流式高频落库抢 SQLite 锁 `[高危]`

- **现象**：运行中保存设置卡死，主界面流式文字停顿。
- **根因**：流式回调每 800ms 抢 `Arc<Mutex<Store>>` 写库，设置读写在同一把锁后面排队。
- **web 版必须实现**：
  1. **delta 不落库**（架构已定）；只在 step 结束落最终 assistant 消息；
  2. 写操作统一走单写通道（短事务，`SetMaxOpenConns(1)`），**禁止在流式循环内做任何 DB 写**；
  3. 设置读取走内存快照（启动时加载 + 变更后更新），不与对话路径争锁；
  4. 需要"崩溃不丢内容"时，用**内存快照 + 定期 checkpoint**，而非高频 DB 写。
- **验收**：流式输出 30s 期间连续保存设置 10 次，断言设置保存 P99 < 200ms、流式无卡顿。

### E2. 全局设置对象整体订阅 `[中]`

- **根因**：上百张 ToolCard 订阅 `s.settings`，保存一次全部重渲染。
- **web 版必须实现**：设置按字段订阅；设置变更只广播变更的 key（`settings.changed {keys:[...]}`），前端按 key 订阅。

### E3. 静态步数上限无法在轨调整 `[中]`

- **现象**：30 步耗尽只能重开对话。
- **web 版必须实现**：`maxSteps` 为会话级可覆盖 + 运行中可调（**每个 step 开始时读取**，不缓存到循环外）；UI 提供"继续推进 +10 步"；同时保留全局默认与硬上限（防失控）。

## F. 安全与路径

### F1. 提示词负向禁令引发过度拒答 `[高危]`

- **现象**：用户要求读 `~/.cargo/config.toml` 或 `../ref_repo`，模型直接拒答"根据安全规则不能访问工作区外"。
- **根因**：system prompt 写「不要访问工作区之外的路径」，模型对否定词极度敏感，把合理需求也拦掉。
- **web 版必须实现**：**prompt 只给正向坐标系**（"当前工作根目录为 X，相对路径以此为基准；外部文件请用绝对路径"），**不写禁止性表述**；安全完全交给运行时守卫 + 审批 UI（审批卡片高亮显示"外部路径"）。
- **验收**：对话中请求读取外部路径，断言模型不拒答、而是触发审批。

### F2. 路径校验误杀新建文件 `[高危]`

- **根因**：`canonicalize()` 对不存在的目标返回 `NotFound` → 被判定为越界。
- **web 版必须实现**：
  1. 校验顺序：`Clean` → `Abs` → 取**最近的已存在父目录** `EvalSymlinks` → 拼接剩余部分 → 再判断前缀；
  2. 写入类操作允许目标不存在（父目录必须存在且在界内）；
  3. 越界不是"直接拒绝"，而是**风险升级**（常规路径自动放行 / 外部路径需审批），与访问模式联动；
  4. 单测覆盖：新建文件、符号链接指向界外、`..` 逃逸、Windows 盘符与大小写。
- **验收**：`write_file` 创建新文件不被判越界；`../outside.txt` 触发审批。

### F3. 主密钥丢失导致全部 API Key 不可用 `[中]`

- **web 版必须实现**：`secret.key` 权限 0600；启动时若 DB 有加密 Key 但密钥缺失/不匹配，**给出明确错误与恢复指引**（不要静默清空）；设置页提供"导出/导入加密配置"与备份提示。

## G. 工具语义

### G1. todo 单轮重复创建与末项残留 `[中]`

- **现象**：一轮对话里出现两张一模一样的清单；交付完成后最后一项仍是空心圆。
- **根因**：① 同一轮多次 `todo` 调用被当成多张清单；② 模型输出终态文本时不会为最后一项再发一次工具调用；③ 前端 `t.status || "done"` 真值短路把 `pending` 误显示。
- **web 版必须实现**：同一 `run_id` 内多次 todo 调用**聚合为一张清单**（保留最新快照 + 事件序列）；Run 正常结束时，把仍为 `pending/in_progress` 的项标注为「未完成」或由系统收敛（明确二选一，不要靠前端兜）；前端禁止用 `||` 做状态兜底，必须显式枚举映射。
- **验收**：单轮内 3 次 todo 调用只显示 1 张卡片；Run 结束后清单状态与 DB 一致。

### G2. "进程不在运行"≠"任务成功" `[中]`

- **根因**：编排工具用 `is_running == false` 判定完成，子任务报错/中断也被报成 🟢 完成。
- **web 版必须实现**：任何异步执行体必须有显式终态枚举（`completed / failed / cancelled / timeout / interrupted`）+ 失败原因字段；**禁止用"没在跑"推断成功**。一期虽无子 Agent，但插件/工具/后台下载同此原则。

## H. 工程环境与运维

### H1. 开发期 DB 文件变更触发无限重编译 `[中]`

- **桌面版教训**：`tauri dev` 监视项目目录，SQLite WAL 变更触发无限重编译，只能把 dev 数据放 `.dev-data/`。
- **web 版必须实现**：dev 数据目录 `data/`（或 `.dev-data/`）加入 `air`/`watcher` 忽略列表；`data/` 加入 `.gitignore`；生产数据目录与源码目录分离。

### H2. 多实例同时写同一 DB `[高危]`

- **web 版必须实现**：启动时对数据目录加**文件锁**（`flock` / Windows `LockFileEx`），已有实例运行则拒绝启动并提示（或提示换端口 + 换数据目录）；端口占用检测失败时打印可读原因，不静默退出。

### H3. 启动失败信息被吞掉 `[中]`

- **桌面版教训**：双击 exe 报错一闪而过，用户看不到原因（脚本专门做"按回车关闭"）。
- **web 版必须实现**：启动失败 → 写 `data/logs/startup-error.log` + 控制台醒目输出 + 非零退出码；`--no-pause`/CI 环境不阻塞等待输入（用 `isatty` 判断）。

### H4. Go/Rust 正则不支持反向引用 `[中]`

- **桌面版教训**：`(?i)<h([1-6])[^>]*>(.*?)</h\1>` 在 Rust `regex` 直接报错（RE2 系不支持 backreference）。**Go 的 `regexp` 同样是 RE2，坑完全一致**。
- **web 版必须实现**：写 HTML/Markdown 清洗正则时不用反向引用与回溯；用字符组替代（`</h[1-6]>`）；复杂解析用 `golang.org/x/net/html` 而非正则。

### H5. 跨平台换行符（Windows 开发 / Linux 部署）`[高危，已落地]`

**故障表现**（三处都是真实会挂）：

| 文件类型 | CRLF 后果 |
| --- | --- |
| `.go` | `gofmt -l` 全量误报（实测 90/90 全部命中）；开发者一旦 `gofmt -w .`，90 个文件换行全改，产生巨量伪 diff |
| `Makefile` | Linux 上 `make` 报 `missing separator`（Tab 被污染） |
| `.sh` | Linux 上 `bad interpreter: /bin/sh^M` |

**根治方式：全部在仓库内，零 git 配置依赖**

1. `.gitattributes` 声明 `* text=auto eol=lf` 兜底 + 关键类型显式声明。
   - `eol` 属性**优先级高于 `core.autocrlf`**，所以协作者本机无论 `autocrlf=true/false/input`，检出结果都一致为 LF —— **克隆后无需改任何配置**。
   - 兜底规则保证未来新增的文本类型（`.toml`/`.proto` 等）自动按 LF，不会因"忘了加一行"而漂移。
2. `.editorconfig` 约束编辑器写盘 LF。
   - ⚠️ **`.gitattributes` 只管 git 检出，管不住编辑器保存**。缺了这层就会出现"重检后是 LF、改一行按 Ctrl+S 又变 CRLF"。
3. 换行符自检（**Windows 开发机直接用 PowerShell，无需 make**）：

   ```powershell
   # 列出全部应为 LF 但被污染成 CRLF 的文件（输出为空即干净）
   git ls-files --eol | Select-String 'w/crlf' | Select-String -NotMatch '\.(ps1|cmd|bat)$'
   ```

   > Windows 开发机通常不装 `make`（且 Makefile 内命令为 Unix 风格），
   > 因此 `make check-eol` **仅在 Linux/CI 上使用**；Windows 用上面的 PowerShell 等价命令。

**例外**：`dev/*.ps1` 保留 CRLF（Windows 专用验证脚本）。**这些脚本不支持在 Linux 执行，请勿在 CI 中调用。**

**排查手法**（判断"真格式问题"还是"换行符误报"）：

```powershell
git ls-files --eol web/embed.go
# i/lf  w/crlf  ← i(LF 入库) / w(CRLF 工作区) 不一致 = 换行符误报，不是格式问题
```

**修复**（无需改 git 配置）：

```bash
git rm -r --cached . && git reset --hard HEAD
```

☠️ 坑：`.gitattributes` 提交后**已检出的 CRLF 文件不会被回溯转换**，必须走上一步强制重检才生效。只 `git add` 提交 `.gitattributes` 是不够的。

### H6. 本地验证统一用 `127.0.0.1:5611` + SSO 免登 `[强制约定]`

**约定（后续所有手工/自动化测试一律遵守）**：

```
http://127.0.0.1:5611/?user_name=admin&pwd=<口令>
```

- 访问主机**必须是 `127.0.0.1`**，不得用 `localhost`；
- 登录方式**优先用 `?user_name=&pwd=` SSO 免登**，不要走登录表单；
- 口令来源：`data/initial_password`（首启生成，两行 = 用户名 / 初始口令）。
  ⚠️ **该文件只是「初始」口令**：一旦改过密码它就是过期值，照抄会得到 `302 → /?sso_error=1`。
  判定方法：免登成功是 `302 → /`（跳回干净首页）；失败是 `302 → /?sso_error=1`。
  忘记当前口令时用下面的登录接口验证，不要反复猜。

**为什么必须固定 `127.0.0.1`（真实踩过）**：

`setSessionCookie`（`internal/api/auth_handler.go:27-35`）写 Cookie 时**不设 `Domain`**，即 host-only Cookie：

| 操作 | 结果 |
| --- | --- |
| 在 `127.0.0.1:5611` 登录 | Cookie 只对 `127.0.0.1` 生效 |
| 再打开 `localhost:5611` | **带不上该 Cookie** → `/auth/me` 恒 401 → 页面渲染成登录页 |
| 此时点「发送」 | 前端判定未登录，**静默无反应**（无报错、DOM 无变化，极易误判为「功能坏了」） |

`localhost` 与 `127.0.0.1` 在浏览器 Cookie 层面是**两个不同 host**，即使指向同一进程也不共享登录态。

**代理会放大该坑**：开发者常开本地代理（本例 `ProxyEnable=1`、`ProxyServer=127.0.0.1:7897`）。虽然 `ProxyOverride` 通常含 `127.*`，但浏览器地址栏若被代理/扩展改写成 `localhost`，就会落入上面的 Cookie 隔离陷阱。表现为「登录成功了，刷新又变未登录」。

**为什么优先 SSO 免登而非表单**：免登由服务端 `302` 直接种 Cookie 并跳转到干净 URL（地址栏不含 query），一步到位且不受前端表单状态影响；表单提交在自动化场景（无头浏览器独立会话）下更容易因 host 漂移而失效。

**排查口令**（判断「登录态问题」还是「功能缺陷」）：

```powershell
# ① 服务端与凭据是否正常（绕过浏览器）
curl.exe -s -i -X POST -H "Content-Type: application/json" `
  --data-binary "@login.json" http://127.0.0.1:5611/api/v1/auth/login
# 期望 200 + Set-Cookie: hg_sess=...; Path=/; HttpOnly; SameSite=Lax（无 Domain 字段）

# ② SSO 免登是否生效（看 302 落点）
curl.exe -s -o NUL -w "code=%{http_code} to=%{redirect_url}`n" `
  "http://127.0.0.1:5611/?user_name=admin&pwd=<当前口令>"
# 成功：302 → http://127.0.0.1:5611/
# 失败：302 → http://127.0.0.1:5611/?sso_error=1   ← 口令不对/已改过

# ③ 两个 host 的登录态是否一致（浏览器问题会体现在这里）
curl.exe -s -o NUL -w "localhost=%{http_code}`n" -H "Authorization: Bearer <token>" http://localhost:5611/api/v1/sessions
curl.exe -s -o NUL -w "127=%{http_code}`n"         -H "Authorization: Bearer <token>" http://127.0.0.1:5611/api/v1/sessions
```

若 ① 正常而浏览器仍 401，就是 host/Cookie 问题，不是代码缺陷 → 换 `127.0.0.1` 重来。

**根治方向（尚未实施，属独立改进项）**：给 Cookie 加 `Domain` 使两个 host 共享（需谨慎，`Domain` 会放宽作用域），或服务端做 host 归一重定向（`localhost` → `127.0.0.1`）。当前以「固定用 `127.0.0.1`」作为约定规避。

### H6.1 忘记口令 → 用 `reset-password` 子命令离线重置

口令彻底忘了（`data/initial_password` 只是首启值，改过就失效）时，**不要去猜、不要手改库**，用内置子命令：

```powershell
# 随机生成新口令并打印（推荐：口令不落在 shell 历史里）
go run ./cmd/harness-go reset-password -user admin -data ./data

# 或显式指定口令（注意：会进 PowerShell 历史记录）
go run ./cmd/harness-go reset-password -user admin -data ./data -password "新的口令至少8位"
```

要点：

- **`-data` 必须是服务端实际使用的数据目录**（默认 `./data`）。目录里没有 `main.db` 时命令会**明确报错并提示**，绝不会静默新建空库——否则会误报成「账号不存在」，把排错引向错误方向。
- 重置会**吊销该账号全部现存登录令牌**（其它设备/浏览器需重新登录），但**不会**影响其它账号。
- 服务端**无需重启**：口令与令牌都读主库，下次登录立即生效。
- 该子命令在 `main()` 里于 `run()` 之前分流，因此**即使服务启动不了**（配置错、端口被占）也能执行。
- ⚠️ 它**刻意不校验旧口令**，所以绝不会暴露成 HTTP 路由——网络侧不存在任何「免旧口令改密」入口。这是安全边界，不要为了「方便」加接口。

### H7. 后台启动服务时 stdout 重定向会连带杀死 app.log `[高危]`

- **现象**：服务进程存活、接口正常响应（curl 200/401），但 `data/app.log` 与访问日志**停在启动那一刻**再无新增，`diff=0`。排查时误以为「请求没到达服务端」。
- **根因**：日志 writer 是 `io.MultiWriter(os.Stdout, rot)`（`cmd/harness-go/main.go:104`）。用 `Start-Process -RedirectStandardOutput` 启动时，重定向管道由**父 PowerShell 会话持有**；父会话被回收/超时终止后管道断裂 → 写 stdout 失败 → **MultiWriter 整条短路** → 连落盘那一半也不再写。并非 `RotationWriter` 缺陷（它本身是无缓冲直写，`internal/observ/rotation.go`）。
- **正确启动方式**（不把 stdout 管道绑到当前会话）：

```powershell
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName = "D:\...\harness-go.exe"
$psi.WorkingDirectory = "D:\...\harness_go"
$psi.UseShellExecute = $true          # 关键：不经过父会话管道
$psi.WindowStyle = [System.Diagnostics.ProcessWindowStyle]::Hidden
[System.Diagnostics.Process]::Start($psi)
```

- **验收**：启动后发一次请求，`(Get-Item data\app.log).Length` 必须增长且尾部出现新 `msg=access` 行。
- **教训**：**「日志不动」不等于「请求没来」**。先验日志管道活性（请求前后比对文件长度），再据此判断请求是否到达，否则会把「日志瞎了」误诊成「功能挂了」。

### A.4 Android 构建链（**已实测出包，不再是「待验证」**）

`Gradle 8.14.3`、`AGP 8.11.1`、`Kotlin 2.2.20`（= Flutter 3.47.9 硬下限 8.14.0 / 8.11.1 / 2.2.20）、

- `compileSdk` 必须 36：`Dependency 'androidx.activity:activity:1.13.0' requires ... version 36 or later`
- desugaring 属性名是 **`coreLibraryDesugaringEnabled`**，写成 `isCoreLibraryDesugaringEnabled` 会报

### A.5 「构建卡死 15 分钟」的排查判据（可复用，别再猜内存）

1. **测 CPU 增量**：20 秒内 <1 秒 → 在等 IO，不是计算，也不是内存不足。
2. **`jstack <daemonPID>`**，命中以下两条即判定「下载中」而非「死锁」：
   - `ParallelResolveArtifactSet$VisitingSet.visit`
   - `org.apache.http.impl.io.SessionInputBufferImpl.streamRead`
3. **`--offline` 反向验证**，直接报出缺哪个构件：
   ```bash
   cd android && ./gradlew :app:assembleDebug --offline
   # → Could not download arm64_v8a_debug-xxx.jar: No cached version available for offline mode
   ```
4. 查 `%USERPROFILE%\.gradle\caches\modules-2\files-2.1\io.flutter\` 下各 ABI 是否齐全。

**附加坑**：Java 不读 `HTTP_PROXY` 环境变量，必须显式写 `-Dhttp.proxyHost/Port` 到 `org.gradle.jvmargs`
或 `~/.gradle/gradle.properties` 的 `systemProp.*`；Gradle wrapper 自身下载（131MB）同样需要，
否则 `.part` 文件恒为 0 字节；改完代理必须 `gradlew --stop` 清 daemon 缓存。

### A.6 Windows 构建：MSVC 必须锁 v143 + NuGet 必须系统级 PATH

| 坑 | 现象 | 根因与处置 |
| --- | --- | --- |
| **MSVC 14.51 硬错误** | `error C2338: STL1011: The /await compiler option ... deprecated` → `flutter_inappwebview_windows_plugin` | VS2026 Insiders 默认 14.51 把旧式 `/await` 协程从警告升为**硬错误**；插件最新稳定版就是 6.1.5（6.2.0 仅 beta）无法升。**处置**：补装 v143 工具集 **+ ATL**，并在 `windows/CMakeLists.txt` 的 `project()` 前注入 `CMAKE_GENERATOR_TOOLSET=v143` |
| **ATL 易漏** | `C1083: 无法打开包括文件: "atlstr.h"` | v143 主体装了但漏 `Microsoft.VisualStudio.Component.VC.14.39.17.9.ATL`，`flutter_secure_storage_windows` 需要 |
| **为何只能工程侧注入** | 环境变量 `CMAKE_GENERATOR_TOOLSET` 报 `will be ignored, because CMAKE_GENERATOR is not set`；改 `CMakeCache.txt` 下次被覆盖回 `INTERNAL=` | Flutter 的 `build_windows.dart` 把参数写死为 `-G <generator> -A <arch>`，**不传 `-T`，也无 additionalCmakeArgs 扩展点**。三种直觉做法均实测失败 |
| **NuGet 系统级 PATH** | `MSB3073: NUGET-NOTFOUND` | 装用户级 PATH 对 MSBuild 子进程无效。必须 `%USERPROFILE%\.nuget-cli` + **系统级(Machine)** PATH |
| **CMakeCache 固化旧 nuget 路径** | `Failed to install nuget package`（而非 not found，极难排查） | 改 nuget 位置后必须**整个删除 `build/windows`**，否则 `CMakeCache.txt` 里 `NUGET:FILEPATH` 仍指向旧 exe |
| **中断 VS Installer 的后果** | `Unable to find suitable Visual Studio toolchain` / CMake `could not find any instance of Visual Studio` | 中断会让 `_Instances\<id>\state.errors.json` 写入 `skippedPackages` → `vswhere` 报 `isComplete=False / isLaunchable=False`。**修复只能重跑 Installer GUI 点「修改→继续」跑完**；命令行 `repair/modify --quiet` 会卡在自更新阶段空退出 |
| **含空格路径丢引号** | `找不到与以下参数匹配的已安装产品: installPath: D:\Program` | `Start-Process -ArgumentList @(...)` 无法为含空格参数加引号，**必须写成 .bat 批处理执行** |
| **Windows 开发者模式** | `pub get` 报 `Building with plugins requires symlink support` | 需 `HKLM\...\AppModelUnlock\AllowDevelopmentWithoutDevLicense=1`，且**重登**才对该用户 token 生效 |

### A.7 相关踩坑（跨端通用教训）

| 坑 | 结论 |
| --- | --- |
| 文档版本组合随 Flutter 升级失效 | 「Gradle 8.7 是 Flutter tool 已知兼容上限」在 3.24 时代成立，3.47.9 已反转为**低于下限**。版本类断言必须标注**验证时的 Flutter 版本**，否则会误导后人 |
| 依赖库"在 pubspec 但代码零引用" | `drift` / `sqlite3_flutter_libs` / `drift_dev` 在 `lib` 与 `test` 均零引用却仍在 pubspec，直接把 NDK 编入构建链。**死依赖必须清理，不能只注释** |
| 平台切换才暴露的构建链问题 | Windows 构建不加载 Android 专属插件（如 `jni`），故 NDK 缺失可长期潜伏。**跨平台项目必须至少各跑一次目标平台的完整构建门禁** |
| **目录看错导致「从未成功」误判** | 旧结论称「`build/` 下无任何 `.apk`」，实际产物在 `build/app/outputs/apk/debug/`，而新路径是 `build/app/outputs/flutter-apk/`。**判定前先列全目录，别只查一个路径** |
| **硬件/环境数据必须现测** | 「15.6G 内存」被当作硬前提写进多个文档，实测 64GB。**机器规格类断言必须带采样时间与命令**（`Get-CimInstance Win32_OperatingSystem`） |
| **Flutter SDK 版本与 .metadata 对账** | 工程 `.metadata` 记录 revision `c197ca5199`，与 SDK 实际 `git describe` 比对可秒判「SDK 是否被降级」。本轮正是靠此发现 SDK 退化到 3.24.5 |

### A.8 桌面端（hd-host）三端联调实测坑（2026-11-11，均已修复）

| 坑 | 现象 | 根因与处置 |
| --- | --- | --- |
| **windows-gnu 构建缺 MinGW** | `cc-rs: failed to find tool "gcc.exe"` / `tauri-winres: NotAttempted("windres")` / `dlltool ... CreateProcess` | rust-toolchain.toml 钉 1.98.1-x86_64-pc-windows-gnu，rustup 自带 self-contained 目录只有 dlltool/ld，**缺 gcc 与 as**。处置：PATH 前置 `C:\msys64\mingw64\bin`，已固化进 `harness_desktop/scripts/dev.ps1`（动态探测、不阻断） |
| **dev.ps1 中文注释吞代码** | 新增的 PATH 注入 foreach 静默不执行、无任何输出 | dev.ps1 是 BOM-less 文件，PowerShell 5.1 按 ANSI/GBK 读：UTF-8 中文注释的奇数字节会把**下一行开头的换行符吞进 GBK 双字节对**，整段代码并入注释。脚本头注释早有「ASCII-only」警告，本次正是踩中。处置：dev.ps1 注释一律 ASCII |
| **Runner 启动即静默秒退** | GUI 拉起 Runner 后 31ms 内退出码 0，设备永不在线，无任何日志 | `Daemon::wait_exit` 在 `child.wait()` 前 `drop(stdin)`——Runner 以「stdin EOF = 宿主已死」自杀（协议硬语义），而 supervise 循环把 wait_exit 当**常规等待入口**，等于每次等待都立刻杀死 Runner。旧注释与行为自相矛盾；集成测试全绿是因为 fake_runner 用例不依赖「活着等 stdin」。处置：wait_exit 期间保持写端打开，wait 返回后再 drop（daemon.rs 已留 2026-11-11 修复注释） |
| **supervise 无法被退出打断** | 修复上条后暴露：GUI 点退出后守护循环卡在 wait_exit 不返回 | wait_exit 阻塞等子进程退出，shutdown 标志只在「退出后」才检查。处置：supervise 里 `tokio::select!` 让「子进程退出」与「shutdown 标志（100ms 分段轮询）」竞速，shutdown 先到则走 `daemon.shutdown()`（关写端→自杀→1s kill 兜底→释放锁）；轮询分支**先睡 100ms 再查标志**，避免与退出事件同时就绪时 select 随机择一造成日志断言 flaky |
| **本地 ws:// 服务端无法配对** | GUI 配对本地 `http://127.0.0.1:5611` 后 Runner 以 NO_AUTH 退出，**且守护循环 repair 分支把密钥链令牌与 profile.json 全部清空** | hd-runner 的地址安全闸门默认拒绝明文 `ws://`（防 `?token=` 局域网裸奔），仅 `--dev` 豁免；而 GUI 拉起 Runner 从不传 `--dev`。回环地址流量不出本机、无嗅探面。处置：宿主按 `ws_url` 是否回环（仅 127.0.0.1/localhost/[::1]）自动追加 `--dev`（daemon.rs `needs_dev_flag`/`runner_args`，6 个单测钉死）；Runner 侧闸门保持严格不动 |
| **GUI 零日志导致排障全靠猜** | 上述三个缺陷叠加时，GUI 内 spawn 失败既无日志也无弹窗 | main.rs 的 `tracing_subscriber_init` 长期是占位实现（注释明说待接线）。处置：接入 tracing-subscriber（stderr + RUST_LOG 覆盖，默认 info），守护循环结束时 warn 输出 last_exit（退出码是判断死因的唯一线索） |
| **Windows 下测试产物被运行中进程锁死** | `cargo build` 报 `os error 32 另一个程序正在使用此文件` | hd-host.exe / fake_runner.exe 在跑时无法重链接。处置：构建前 `taskkill /F /IM hd-host.exe`（并确认 fake_runner 无残留） |
| **集成测试抢真实实例锁** | `runner_missing_reports_search_path` 单独跑过、本机有 GUI 时必挂（ExternallyRunning） | bootstrap 测试的 Daemon 未注入锁路径，默认锁指向真实用户数据目录。处置：测试用 `with_lock_path(tempdir)` 隔离（supervise_e2e 早有此纪律，bootstrap 单测补齐） |
| **API 测试中文乱码被误判为服务端 bug** | curl 直发中文后入库乱码 | Git Bash 控制台把命令行里的中文按本地码页传给 curl。**不是服务端缺陷**：用 UTF-8 文件体（`--data-binary @file`）即正常。回归判定时必须区分「输入通道乱码」与「存储/显示乱码」 |

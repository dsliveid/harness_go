# 系统内置工具的可安装性与多端协同设计约定

> 状态：v0.1（2026-10-30，demo 原型「高级 → 工具 / MCP / 技能」四段视图改造同步落地）
> 适用范围：`harness_go`（Web 版）与 `harness_mini`（桌面版）共用的能力（工具 / MCP / 技能）模型
> 铁律级别：本文 §2 的「可安装性硬约束」为长期约束，任何新增内置工具、MCP、技能都必须满足。

---

## 1. 背景与目标

产品形态是「服务端大脑 + 多端肢体」：

- **Web 服务端**：Agent 编排、模型通道、审批、事件总线、数据落库（大脑）。
- **桌面客户端 / 移动端 PWA**：文件系统、终端、浏览器自动化、通知等本机能力（肢体）。

因此「系统内置工具」不能只活在服务端进程里 —— 若工具实现只依赖服务端环境，客户端就永远无法在本地执行，
只能每次把文件内容/命令输出往返上云，既慢又泄露数据，还会把工具输出全部烧成 token。

**目标：所有系统内置工具都必须具备「可安装性」**，即同一份能力可以被打包成制品（artifact），
由服务端下发到客户端安装、在客户端本地执行，且行为与服务端一致。

---

## 2. 可安装性硬约束（铁律）

1. **能力必须有 manifest**：每个内置工具 / MCP / 技能都要能导出制品清单
   （`name`、`version`、`kind`、`risk`、`deps`、`entrypoint`、`checksum`、`signature`、`min_host_version`）。
2. **实现必须与运行环境解耦**：工具实现不得直接引用服务端单例（全局并发信号量、SQLite 连接池、事件总线实例），
   须通过「能力契约」注入：`fs` / `shell` / `net` / `model` / `store` 六类端口。本地就本地实现，服务端就代理实现。
3. **要么可安装、要么显式声明不可安装**：不允许「含糊的未知状态」。
   - 可安装：`installable = true`，给出 `mode`（`随包内置` / `按需下发`）与客户端依赖 `deps`。
   - 不可独立安装：`installable = false`，必须在工具描述中说明「仅服务端执行，客户端通过 API 代理调用」，
     例如 `spawn_subagent` / `spawn_subprocess`（依赖服务端调度与全局并发 semaphore）。
4. **依赖必须可探测、可降级**：客户端安装前探测 `deps`（`node>=18`、`chromium`、`model:vision`、`shell` 等）。
   缺失则安装进入 `blocked` 状态并给出修复建议，**禁止静默安装后在运行期崩溃**。
5. **安装必须幂等**：以 `(kind, name)` + `content_hash` 作为幂等键；重复下发为 no-op，版本变化走升级流程。
6. **风险与审批不可绕过**：安装动作本身是一次「能力变更」，需按风险等级走审批
   （`readonly` 可自动放行；`write` / `command` 需确认；`danger` 逐次确认）。制品签名缺失时默认拒绝安装。
7. **命名空间不冲突**：同名能力「本地优先，内置生效」；MCP 工具以 `mcp:<server>.<tool>` 命名；
   拓展能力以 `ext:<name>` 前缀注入，**严禁覆盖系统内置工具**。
8. **可回滚**：每次安装记录 `install_id`、来源版本、安装时间、执行端；卸载/回滚不得破坏工作区数据，
   只回收制品与注册项。

## 3. 四个来源层级（UI 与数据模型统一口径）

「高级 → 工具 / MCP / 技能」三页的二级视图统一为四段，数据模型用 `ExtOrigin` 表达：

| 视图 | 语义 | 数据来源 | 典型操作 |
| --- | --- | --- | --- |
| **系统内置** | 随服务端发布，默认可用，具备可安装性 | `toolList` / `mcpServers(origin=builtin)` / `skills(origin=builtin)` | 启停、安装到客户端、一键下发 |
| **已安装** | 本端已落地可用（含拓展产出的实例） | 市场下载制品、本地技能、`origin=installed` / `extended` 的实例 | 停用、卸载、升级、删除 |
| **市场** | 远端 registry 候选池（尚未安装） | `registryItems`（`kind` = plugin / mcp / skill） | 安装（需审批）、查看依赖与签名 |
| **拓展** | **程序在开发过程中为自己扩展的能力** | `extensions`（`kind` = tool / mcp / skill） | 自检、安装、停用、卸载、同步到客户端 |

> 「拓展」不是第四种来源渠道，而是**自演化产物的治理面**：Agent 在会话中为自己写工具/技能/MCP Server，
> 草稿必须通过自检 + 用户审批后才能安装（安装后进入「已安装」）。

### 3.1 拓展项（ExtensionItem）生命周期

```
draft（草稿，自检中） --自检通过 + 审批--> installed（已安装，可下发客户端）
                                          │
                            ┌─────────────┴─────────────┐
                        disabled（停用）            remove（卸载，回收制品）
                            │
                         启用 → installed
```

约束：

- `selfTest = failed` 的草稿**不可安装**（按钮禁用并给出原因），只能修复后重跑自检。
- 拓展产出必须记录出处（`generatedBy`：会话 / 计划），便于追溯与回滚。
- 拓展项**不允许**自己给自己签名；`unsigned` 状态在 UI 上必须可见。
- 拓展安装后与内置工具一样进入「已安装」，并可 `同步到客户端`。

## 4. 安装协议（服务端 → 客户端）

### 4.1 制品 manifest（示例）

```json
{
  "kind": "tool",
  "name": "read_file",
  "version": "1.0.0",
  "risk": "readonly",
  "install_mode": "随包内置",
  "deps": ["fs"],
  "entrypoint": "bin/harness-tool-readfile",
  "content_hash": "sha256:...",
  "signature": "ed25519:...",
  "min_host_version": "0.9.0"
}
```

### 4.2 下发与安装流程

1. 客户端建立长连接（SSE/WS）并上报 `device_id`、平台、能力。
2. 服务端按客户端能力筛选 `installable=true` 且 `deps` 满足的制品 → 下发 manifest（不满足的标 `blocked` + 缺失项）。
3. 客户端校验 `signature` + `content_hash` → 走审批（按 `risk`）→ 落盘到本地能力目录 → 注册到本地工具表 → 回执。
4. **离线端排队**：客户端不在线时进入待安装队列，上线后自动安装（幂等，已装则跳过）。
5. 安装回执写入服务端 `device_artifacts`，并在「高级 → 工作空间 / 端节点」可见。

### 4.3 建议的数据表

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `artifacts` | 制品目录（内置 + 市场 + 拓展） | `kind`、`name`、`version`、`risk`、`install_mode`、`deps`、`content_hash`、`signature`、`origin` |
| `artifact_installs` | 本端安装记录 | `artifact_id`、`installed_at`、`state`、`enabled` |
| `devices` | 端节点 | `id`、`platform`、`online`、`last_sync_at`、`capabilities` |
| `device_artifacts` | 端 × 制品安装矩阵 | `device_id`、`artifact_id`、`state`(queued/installing/installed/blocked/failed)、`installed_at` |
| `extensions` | 拓展治理面 | `kind`、`name`、`version`、`state`、`self_test`、`generated_by`、`risk` |

> 与 §7（token 治理）协同：所有能力定义仍走「索引 + 按需加载」，**下发安装不影响注入预算**；
> 未注入定义但已安装的能力仍可执行（宽进严出）。

## 5. 客户端侧执行语义

- 客户端工具调用由**服务端 Agent 决策、客户端执行**：服务端下发 `tool.invoke`（含 `run_id`、`call_id`、参数、超时），
  客户端执行并回传结果；幂等由 `call_id` 保证，重复派发不重复执行。
- 审批语义不变：客户端本地写入/命令仍需审批（可在客户端就地审批，回执合并入同一 `tool_event`）。
- 事件与消息仍以服务端 DB 为准；客户端只负责执行与本地落盘。
- 断线重连：客户端重连后拉取未回执的 `call_id` 列表，避免「执行了但没回传」的双重执行。

---

## 6. 技能（SOP）的可安装性

- 内置技能（如 `web-autonomous-test`、`plan-first-workflow`）以目录形式下发：`.harness/skills/<name>/`（脚本 + 说明）。
- 技能索引（40 token 级摘要）常驻注入；技能正文按需 `load_skill` 加载，避免撑爆上下文。
- 客户端执行技能必须在沙箱内（限制可执行命令白名单、禁止外网直连，除非脚本声明）。
- 技能升级以 **同名覆盖 + 保留 `previous_version`** 的方式实现，便于回滚。

---

## 7. 与既有架构的关系

| 机制 | 关系 |
| --- | --- |
| 审批（approvals / approval_rules） | 「安装」「首次执行」「危险命令」三类动作共享同一审批模型 |
| 事件模型（per-Run ring buffer） | 新增 `capability.install.*` 里程碑事件（安装开始/成功/失败/阻塞），delta 不落库 |
| Run 状态机 | 安装阻塞不改变 Run 状态；工具不可用时按「工具失败」回传给模型，由模型降级决策 |
| token 治理 | 能力定义走渐进披露；安装矩阵不进入 prompt，仅注入「可用能力摘要」 |
| 桌面版对齐 | 桌面版 `commands.rs` 的本地工具实现即客户端执行的参考实现，需抽出可复用的能力契约层 |

## 8. 验收清单（新增内置能力时逐条自查）

- [ ] 是否提供 manifest，且 `install_mode` / `deps` 填写完整？
- [ ] 实现是否只依赖 `fs` / `shell` / `net` / `model` / `store` 端口，而非服务端单例？
- [ ] 在客户端安装后能否本地执行（有对应实现或明确的代理回退）？
- [ ] 依赖缺失时是否进入 `blocked` 并给出修复建议，而非运行期崩溃？
- [ ] 安装是否幂等（`content_hash`）、可回滚、可卸载？
- [ ] 风险等级与审批策略是否一致？签名缺失是否默认拒绝？
- [ ] 是否遵循命名空间约定（`mcp:` / `ext:`），不覆盖内置工具？
- [ ] UI 是否在「系统内置 / 已安装 / 市场 / 拓展」四段中正确归类？

## 0. 优先级口径（用户见解 → 工程口径）

| 用户口径 | 工程口径 | 落位 |
| --- | --- | --- |
| ① 先做基础稳定架构 + 稳定健壮的对话能力，**架构内定义好各种协议**以满足可扩展（接插件/外部插件） | 先交付「Run 状态机 + 事件模型 + 落库铁律 + 协议骨架」，**协议不留实现也可以，但必须有符合性样例** | **阶段 A** |
| ② 再做服务端前端，demo 已像素级完成，按 demo 还原，后端开发要配合前端对接 | 前端不是最后一个作业包，而是**与 A 并行、贯穿全程的 B 线**；`api/openapi.yaml` 为双方唯一物理边界 | **阶段 B（贯穿）** |
| ③ 最后才是各种内部工具能力和其他功能 | 工具能力放在协议验证之后；但**审批闸门属内核不属工具**，必须留在 A | **阶段 E/F/G** |

## 1. 对你判断的校准：认同 3 点，修正 4 点

### 1.1 认同（不改）
1. **对话内核是地基**：Run 状态机、per-Run 事件环、`消息以 DB 为准`、per-session 串行 —— 这四条决定了后面所有功能能不能长上去，先稳它是对的。
2. **协议先行**：45 个工具 + 插件市场 + 多端 Runner，一旦工具契约形状错了，会同时波及 `prompt` 组装、审批判定、前端 `ToolCard` 三处返工。
3. **前端是既成资产**：demo 已完成像素级与交互，后端**适配前端契约**成本远低于让前端重做，这条判断完全正确。

### 1.2 修正 1：协议必须配 conformance fixture，否则是纸上设计
只写协议文档不写实现，等到接工具时 90% 要改。**「定义好协议」的判据 = 每类协议各有 1 个最小可执行样例 + 断言测试**：

| 协议 | 最小样例（fixture） | 阶段 |
| --- | --- | --- |
| 工具契约 | 1 个 `echo` 工具被模型真实调用并落 `tool_events` | A-10 |
| 事件协议 | 事件序列回放断言（含 `v`/`seq`） | A-4 |
| API 契约 | `openapi.yaml` → 生成 TS 类型 → 前后端编译期对齐 | A-10 |
| SSE 传输 | `Last-Event-ID` 断线重连补发断言 | A-8 |
| 插件协议 | 1 个假 MCP Server（stdio/SSE/HTTP 三传输） | D |
| 设备协议 | 1 个假 Runner 脚本应答 `ping/task.dispatch` | C |
| 审批协议 | 超时视为拒绝 + 原因回传模型 | A-10 |

> 结论：协议**形状**在阶段 A 全部定死；协议的**多实现**分散到 C/D 阶段，但每类都有 fixture 兜底。

### 1.3 修正 2：多端协同的**字段现在就要预埋**（表可后加，列不能后加）
既然架构已定为 HALO（中枢 + 端侧 Runner），有三类东西**现在不预留、后面就要写迁移改表 + 改协议**：

| 预留项 | 位置 | 为什么现在做 |
| --- | --- | --- |
| `runs.executor` / `runs.device_id` | A-3 建表 | 执行面下沉是架构级决策，Run 必须能记录"谁在执行" |
| `tool_events.executor` / `device_id` / `source_trust` | A-3 建表 | 端侧结果"不可信"（不变量 4），审计必须带来源与信任级 |
| 事件 `v`（protocol_version） | A-4 事件结构 | 端版本漂移是头号风险（`min_protocol`），首版就要有版本位 |
| 工具契约 7 字段（`executor` / `capabilities` / `cost_tokens` / `defer_loading`） | A-10 | 归属路由与 Token 治理都挂在这 4 个字段上 |
| `protocol_version` 在 `/healthz` 与设备握手 | A-8 | 双代兼容窗口的前提 |
| **`blobs` 会话级 CAS + 主库摘要冗余列** | A-3 | 大对象内联会重演桌面端 212MB；分库后列表/统计必须靠主库摘要列，否则要扫全部会话库 |

**不预埋**：`devices` / `capabilities` / `session_leases` / `tool_packages` 四张表 → 在阶段 C/D 用 `0002_*.sql` 增量迁移建。理由：SQLite 加表是 trivial 操作，过早建空表只增加维护负担。

### 1.4 修正 3：前端还原不能做「最后一个作业包」
demo 有 7 个功能模块、41 个组件。如果等后端全做完再一次性对接，会造成：①联调期 bug 集中爆发，②前端长时间空转，③契约错配发现太晚。改为 **B 线分 6 片，每片绑定一个后端作业包**（详见 §4）。这也直接落实你说的"后端开发时需要考虑前端对接"。

### 1.5 修正 4：审批引擎属于内核，不能延后到"工具能力"
`waiting_approval` 是 Run 状态机的一个正式状态，前端 `ApprovalBar` 是对话流的一部分。若等到阶段 F 才做，A 阶段的 Run 状态机就是残缺的，后面要改状态机 → 违反 ADR 的"状态迁移单点收口"。**审批闸门留在 A（A-7/A-10），只是没有真实工具可审批**，用 fixture 工具验证。

### 1.6 补充：Token 治理必须排在工具市场之前
`多端协同架构可行性方案.md` §0 的核心结论：**"不做治理，工具市场一上线就自我毒化"**。所以 D（Token 治理）必须早于 E（插件与市场）。这是一个与直觉相反的排序，但成本差异极大：治理晚做 = 市场包格式要重定 + 已上线工具要重写描述。

### 1.7 v2.4 三条新决策（用户 2026-11）

| # | 决策 | 结论 | 影响 |
| --- | --- | --- | --- |
| **D10** | **SOP 不做渐进披露** | SOP **全量注入 + 硬上限**（≤6 条 × ≤150 token ≈ 0.9k）；取消 `always / auto_attach / agent_requested / manual` 四类机制与索引；**非必要 SOP 沉淀到 skill**（skill 本身走按需加载，天然承接"可选流程"）。理由：SOP 是低频变更的项目级规范，数量本就少，做索引的收益（省 ~0.4k）不抵一套路径匹配逻辑的维护成本 | 阶段 D 8 → 7 人日；阶段 G 的 `sop` 插件简化为「文件 + 全量注入 + 上限校验」 |
| **D11** | **工具 `Tier` 三档显式标记** | 废弃 `defer_loading: bool`，改 `tier`：`core`（**基础工具**，全量定义注入）/ `deferred`（仅名称 + 一行描述进索引）/ `on_demand`（零注入，仅 UI 可启用）。**数量不设硬上限**（`core_soft_limit=8`/`deferred_soft_limit=60` 仅告警不阻断），**分组可手动调整**：插件默认 < 全局 `settings.tools.tiers` < 会话 `session_settings` 三层覆盖，UI 支持拖拽切换 | 插件体系设计 §3.3；A-10 契约；`/api/v1/tools` 返回 tier/default_tier/cost；`/api/v1/tools/injection` 返回注入预算明细 |
| **D12** | **工具能力与基础服务代码分离** | 四层：`pkg/toolapi`（公开契约，零内核依赖）/ `internal/tools`（注册·路由·加载，**无任何具体工具**）/ `internal/plugins/<name>`（一插件一独立包 + `manifest.json`）/ `cmd/harness-go/plugins.go`（唯一装配点）。工具只能通过 **`Host` 接口**拿受控能力，`depguard` 禁止插件 import 内核实现 | A-10 扩为「协议 + Host + Manifest + tier + 装配骨架」；F 阶段每插件独立包；E 阶段市场包复用同一 manifest |
| **D13** | **长任务 / browser / collaborator 要做，growth 保留工具** | 三者**以工具为入口**（插件 `browser`/`subagent`/`collaborator`/`long-task`），**基础服务保留协议与状态机**：`Host.Spawn()`（嵌套 Run，受 max_depth 与配额约束）、`Host.Tasks()`（长任务状态机 + 检查点）、`Host.Snapshots()`（快照引用）。`growth` 只保留轻量工具（`record_growth`/`list_growths`/`apply_growth`），落 `<ws>/.harness/memory/growth/`，不建状态机 | 覆盖 2026-10-28 评估文档的旧「不做」结论；F/G 阶段范围按此执行 |
| **D14** | **WASM 一期不做**（预留） | 第三方工具包沙箱改用**子进程 + stdio JSON-RPC（复用 MCP 协议）**：OS 进程边界即隔离，复用度 ~80%，新增成本≈0。WASM 真正刚需是「服务端多租户执行不可信代码」，本项目本地单机为一等公民，暂不适用。保留 `Manifest.kind:"wasm"` + `internal/plugins/wasm/` 占位；升级触发条件：①上线云端多租户 或 ②市场向不可信第三方开放且要求服务端执行 | 阶段 E 12 → 9 人日；插件体系设计 §3.5 |

> 三者共同指向一个目标：**内核只留协议与调度，能力全部外置为可独立演进、可独立裁剪、可独立测试的单元**。这也是"架构内定义好协议以支持接入插件与外部插件"的落地形态。

## 附录 A：认证与单点登录免登入口（A-9 详设）

**需求**：访问 `http://<host>:<port>/?user_name=xxxx&pwd=xxxx` 即自动进主页面，免去登录步骤（供 AI 调试、内网门户跳转）。

**核心风险**：URL 明文密码会污染 ①浏览器历史 ②`Referer` ③access log ④代理网关日志 ⑤截图分享。因此**禁止在前端 JS 解析凭据**，改由服务端入口拦截 + 302 剥离。

**入口契约**
```
GET /?user_name=<name>&pwd=<pwd>[&redirect=<path>][&ts=<unix>&sign=<hmac>]
```

| 模式（`auth.sso_mode`） | 说明 | 适用形态 |
| --- | --- | --- |
| `plain`（`local` 默认） | 直接校验 `user_name` + `pwd` | 本机 / 内网调试 |
| `signed`（推荐） | `sign = HMAC-SHA256(user_name + "\n" + ts + "\n" + ip, secret)`，`|now-ts| ≤ 60s` 防重放，`pwd` 可完全不出现 | `server` / `cloud` |
| `both` | 两者接受 | 迁移期 |

**服务端处理链路**（`GET /` 命中且带 `user_name`）
1. 检查 `auth.sso_enabled`（`local` 默认 true，`server`/`cloud` 默认 false）→ 否则 403 `auth.sso.disabled`
2. **独立限流**：5 次/分钟/IP → 429 `auth.rate_limited`
3. argon2id 比对 `users.password_hash`；失败统一 401 `auth.invalid_credentials`，**不区分「用户不存在/密码错误」**
4. 签发会话 `api_tokens(kind='web_session', expires_at=+7d)`，库内只存哈希
5. `Set-Cookie: hg_sess=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800`（https 自动 `Secure`）
6. **302 → `/?redirect=<path>`（不含凭据）**：地址栏、历史、`Referer` 从此干净
7. 审计 `auth.sso {user, ip, ua, result}`；`pwd`/`sign` **永不落日志**（query 白名单脱敏，仅保留 `a***n`）
8. 所有 HTML 响应加 `Referrer-Policy: no-referrer` + `Cache-Control: no-store`

**前端兜底自愈**（vite dev / 纯静态部署）：`LoginPage` 挂载时检测 `location.search` → `POST /api/v1/auth/sso` → 成功后 `history.replaceState` 清 query；失败清 query 并提示「凭据无效」，不显示具体原因。

**认证体系**：`users` 表（**表数 9 → 10**）+ `api_tokens` 扩展 `kind('api'|'web_session'|'sso')`/`user_id`/`expires_at`/`last_used_at`/`revoked_at`；鉴权中间件优先 `Bearer`，其次 Cookie `hg_sess`；首启按 `HARNESS_USER`/`HARNESS_PWD` 引导建账号，缺省 `admin` + 随机口令写 `data/initial_password`(0600)，**禁止出厂弱口令**。

**端点**：`POST /api/v1/auth/login` · `GET /api/v1/auth/me`（首屏静默探测，避免闪登录页）· `POST /api/v1/auth/logout` · `POST /api/v1/auth/sso` · `POST /api/v1/auth/password`

**验收**：带参 URL 打开→主页面且地址栏无 query；错密码→登录页提示不暴露原因；连错 6 次→429；日志搜 `pwd` 零命中；`signed` 模式 ts 超时→401 `auth.sign_expired`。

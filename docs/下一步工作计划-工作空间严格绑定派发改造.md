### 设计要点

**R2 只拦「设备离线」一种情形**：未绑定 / 设备已删 / 已解绑属归属异常，本就由 `resolveToolPolicy` 判 `none`（工具全禁），但**不阻断对话**——强行拦会改变历史会话可访问性，超出需求范围。

**两层防御不可替代**：
- 入口层（R2）挡「发起」：设备离线时对话根本不可开始；
- 上下文层（`resolveToolPolicy`）挡「跑一半掉线」：Run 进行中设备离线 → 工具被拒 → R3 自动中断。

**R3 的死锁防护**：`CancelByDevice` 先在锁内快照并摘除索引，再在**锁外**执行 `cancel()`——cancel 会触发引擎回调并可能重入本结构，持锁调用有死锁风险。

### 宽限期取值依据（已核实）

| 约束 | 实测值 | 出处 | 含义 |
| --- | --- | --- | --- |
| 心跳 / 判离线 | 15s / 45s | `config.go:321-322` | "立即"的真实最坏延迟 = 45s |
| 任务派发 TTL | **600s** | `dispatcher.go:58`、`config.go:323` | 唯一硬上限，宽限期须远小于此 |
| Run ctx | **无 deadline** | `run_service.go:470` `WithCancel(WithoutCancel(ctx))` | ✅ 可安全挂起，不会被上层超时杀掉 |
| 幂等缓存 TTL | **300s** | `dispatcher.go:62` `dispatchHistoryTTL` | 宽限期不宜超过此值，否则重连后重派被当新任务重复执行 |
| **建议值** | **90s**（可配 `devices.reconnect_grace_s`） | — | 端到端 45+90=135s；占 TaskTTL 15%；上限不超 180s |

### 关键设计决策

**暂停态不新增持久化 Run 状态**：`model.RunStatus` 现有 7 态无 paused。新增需 DB 迁移 + 引擎迁移 + 恢复逻辑，且进程重启后无法判断该恢复为暂停还是运行。改为：Run 保持 `running`，"重连中"是"执行面可用性 + 宽限期计时"的**派生 UI 态**（复用 `StateBus` 三态事件派生）；进程重启由既有 `RunStatus.IsUnfinished()` 扫描收敛为 `interrupted`，零新状态机分支。

**审批失效的写入顺序不可颠倒**：`waiting_approval` 的 Run 已登记在 `runDevices` 反向索引（`registerCancelForDevice` 不看 Run 状态）。若先 `CancelByDevice` 再写审计，待决项会失去归属而**永久悬挂**，前端出现"永远等不到的待审批项"。

**禁止新建会话的判定条件是"归属执行面不可用"而非"无绑定设备"**：绑定 ws-server 的纯对话会话恒可用，若写成"无设备即拒绝"会误杀日常最常用场景。

### 阶段二之二：无降级旁路与生命周期三态（v3 新增，必做）

**T7. 派发层收紧为"唯一执行面或零"（🔴 最高优先，必须先于 T8/T9）**
- 位置：`internal/tools/device_runner.go`（`tryDevice`，`:115-129`）
- 现状缺陷：`:119` `if r.devices.Online() <= 0 { return ..., false }` 判的是**全局在线设备数**，且返回 `false` = **静默降级为服务端本地执行**。
- 动作：
  - 删除 `r.devices.Online() <= 0` 这条全局判定；
  - 改为按 `req.ExecutionDeviceID` 判定：为空（服务端执行面）→ 不进入端侧路径；非空但不在线 → **返回明确的执行面不可用错误，既不在服务端执行、也不改派**；
  - 与 `dispatcher.candidates()` 的"指定设备则只用它"配合，确保不会回退到其他在线设备。
- 为什么必须最先做：本项不修，权 15 的"宽进严出"（模型可调用未注入工具）会绕过装配期门控，导致"主设备离线但活被别的设备或在服务端干了"，整个 v3 定案不成立。
- 验收：`device_runner_test.go` 新增用例——目标设备离线 + 另一设备在线 → 不派发给另一设备、且**本地执行器零调用**。

**T8. 会话暂停/冻结门控**
- 位置：`internal/api/handler.go`（`createSession`，`:113`） + `internal/service/session_service.go`（`Create`，`:64`）
- 动作（双层，沿用既有"端侧自律 + 服务端兜底"模式）：
  - handler 层：请求归属工作空间的执行面离线 → 立即返回错误码，前端友好提示；
  - service 层：作为唯一权威落库点再判一次（防绕过 API 直调）。
- **判定条件**：`唯一执行面为客户端设备 且 该设备不在线`（或已冻结）。**不得写成"无绑定设备即拒绝"**——绑 `ws-server` 的纯对话会话恒可用（`session_workspace_required_test.go:34` 有相关用例）。
- 错误码：复用 `apperr.CodeDeviceOffline`（`device.offline`，409）；冻结态可另加 `session.frozen` 便于前端区分文案。

**T9. 宽限期状态机（暂停 → 续跑 / 届满终止）**
- 位置：`cmd/harness-go/main.go`（Hub `OnOffline` 回调，`:692-713`）+ `internal/service/run_service.go`
- 动作：
  - **删除** 离线下立即 `CancelByDevice` 的调用，改为启动一个宽限期定时器（`devices.reconnect_grace_s`，默认 90s，自"判定离线"起算）；
  - 定时器到期且设备仍不在线 → 执行 `CancelByDevice` 并将会话标记冻结；
  - `OnOnline` 回调中取消定时器、清除冻结标记；
  - 定时器表需与 `cancels` 同生命周期，Run 终态时清理，避免泄漏；
  - 进程重启后无需恢复定时器：既有 `RunStatus.IsUnfinished()` 扫描会把未完成 Run 收敛为 `interrupted`。
- 暂停态的实现要点：**不新增持久化 Run 状态**，"重连中"由 `StateBus` 的设备三态事件 + 冻结标记在 UI 派生；服务端侧只需"拒绝新 Run/新会话/审批决策 + 挂起派发"。
- 挂起派发：在 T7 的派发路径上，若执行面处于暂停态（离线但宽限期未满）→ **阻塞等待**（带 ctx 取消）直至上线或宽限期届满，不返回失败、不降级。
- 验收：`run_cancel_by_device_test.go` 需回归并新增"离线后 90s 内不取消、届满才取消"的用例（用可注入的 clock / 短宽限期）。

**T10. 待审批项失效 + 审计（🟠 顺序约束）**
- 位置：`internal/store`（审批仓储）+ `internal/service/run_service.go`
- 动作：
  - 新增决策取值 `invalidated`（**严禁复用 `deny`**），并新增 `actor`（`user` / `system`）与 `reason`（`execution_surface_offline`）字段或复用现有 reason 列；
  - 冻结流程内**先**写全部待决项失效审计、**再**调用 `CancelByDevice`；
  - 审计需记录：执行面标识、宽限期届满时刻、原发起端标识。
- 为什么是这个顺序：`waiting_approval` 的 Run 已登记在 `runDevices`（`run_service.go:754`），先取消会让待决项失去归属而永久悬挂。
- 验收：新增用例断言——离线届满后审批记录为 `invalidated`/`system`，且对应 Run 为 `cancelled`；两件事都发生且顺序正确。

**T11. 主设备语义固化（文档与测试）**
- `Workspace.DeviceID` 单外键即"唯一执行面"，**不新增多设备关联表**；
- 新增测试锁定"一个工作空间至多一台设备"的语义（防止未来误加多设备）；
- `DevicePickFunc` 及"策略设备离线回退其他设备"分支标记 `deprecated`，由 `device.strict_ownership`（默认 true）关闭。

## 2. 验收标准

1. 工作空间 A 绑定桌面 1；桌面 2 在线、桌面 1 离线；在 A 内调用 `run_command`（executor=device）→ **工具已整体剔除，直接返回执行面不可用错误；绝不出现桌面 2 执行的 tool_event，也绝不在服务端执行**（tool_events 元数据 device_id 断言 + executor 断言）；
2. 在 A 内调用目录列举 → `fs.host_offline`，绝不返回其他设备或服务端目录；
3. 桌面 1 重新上线 → 恢复派发到桌面 1；
4. ws-server 空间不受影响（全部走服务端执行面）；
5. **生命周期三态**：
   - 桌面 1 离线 → 会话立即暂停：新 Run 被拒（`device.offline`）、新建归属该空间的会话被拒、审批决策被拒；
   - 宽限期内（< 90s）桌面 1 重连 → 被挂起的在途派发**按原 task_id 原位续跑**，不重复执行（tool_events 只有一条）；
   - 宽限期届满 → 会话冻结只读（历史可读）；**待决审批项先被置为 `invalidated`（来源=系统），再终止在途 Run**（断言审计记录 + Run 终态）；冻结后新建归属该空间的会话被拒；
6. 绑定 ws-server 的纯对话会话在任何设备离线期间**始终可用**（不会被"无设备即拒绝"误杀）；
7. `go test ./...` 全绿。

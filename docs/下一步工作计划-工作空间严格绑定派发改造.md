# 下一步工作计划：执行派发"工作空间严格归属"改造

> 决策背景：2026-11-12 用户确认执行派发采用**工作空间严格归属**模型（放弃多设备策略分配）——会话归属工作空间，工作空间与设备建立绑定关系（**一台或多台**），派发目标只在归属集合内确定、绝不超出集合。
> 两种粒度：归属集合仅一台设备 = **单设备锚定**（该会话全部派发恒指向它，离线按类别降级、绝不改派其他设备）；归属集合多台设备 = **多设备协作**（同一会话内按工具执行端归属与能力标签在集合内确定目标，按（会话,设备）分账并做派发前路径归属校验）。单设备锚定是多设备协作的**下位情形**，改造时先落地单设备锚定，再按需开放多设备归属。
> 当前状态：专利文档已按 v1.6 口径改写（权利要求 / 正式交底书 / 附图）；**代码尚未改造**——当前派发请求未携带 DeviceID，走"首个在线设备"兜底（见下"现状差距"）。

>

## 1. 改造项清单（按依赖顺序）

### 阶段一：核心链路打通（必做，约 3 个文件）

**T1. 会话层透出归属目标设备 ID**
- 位置：`internal/service/run_service.go`（CreateRunAs 内，构造 agent.RunRequest 处）
- 动作：Run 装配时读取 `sess.WorkspaceID → Workspaces().Get → ws.DeviceID`，随 RunRequest 下传（新增字段如 `BoundDeviceID string`）；
- 注意：`ws-server`（DeviceID 为空）→ BoundDeviceID 为空 = 服务端本地执行面，语义不变；
- 失败处理：工作空间悬空时 conversationOnly 已 fail-closed 禁工具，此处天然安全。
- 多设备预留：多设备协作文档中该字段改为"归属集合内的目标设备"，由归属解析统一给出（当前一对一关系下解析结果即 ws.DeviceID）。

**T2. 工具层把归属目标设备写入派发请求**
- 位置：`internal/tools/device_runner.go`（tryDevice 内构造 `DeviceTask{}` 处）
- 动作：`DeviceTask.DeviceID = req.BoundDeviceID`（RunRequest 新字段透传）；
- 语义变化：端侧执行工具（executor=device/any）只发往归属集合内的目标设备；该设备不在线 → Dispatcher 返回 `ErrDeviceUnavailable`（candidates 分支 1 现成行为）→ Runner 按**现有降级类别**处理：可降级工具静默切服务端执行面，目录列举类返回 `fs.host_offline`——**与专利 D1/D2 完全一致，零新增语义**。

**T3. Dispatcher 移除"多设备挑选/回退"路径**（语义收紧）
- 位置：`internal/device/dispatcher.go`（candidates()）
- 动作：
  - `Pick` 策略与"策略选中设备离线回退其他设备"逻辑**保留代码但标记 deprecated**（或由配置开关 `device.strict_ownership` 默认 true 关闭）——避免删掉 `DevicePickFunc` 接口引发连锁改动；
  - 实际生效路径：无 DeviceID 且无 Pick → **不再取"ID 最小的在线设备"**，直接返回 nil（无可派发设备）→ 走降级类别；
- 验收：新增单测锁定"目标设备离线 + 另一设备在线 → 不派发给另一设备"。
- 多设备协作扩展点（暂不实施）：多设备归属下，候选集 = 归属集合 ∩ 在线 ∩ 能力匹配，仍不得超出归属集合。

## 2. 验收标准

1. 工作空间 A 绑定桌面 1；桌面 2 在线、桌面 1 离线；在 A 内调用 `run_command`（executor=device）→ **结果为静默降级本地执行（或按类别的明确错误），绝不出现桌面 2 执行的 tool_event**（tool_events 元数据 device_id 断言）；
2. 在 A 内调用目录列举 → `fs.host_offline`，绝不返回其他设备或服务端目录；
3. 桌面 1 重新上线 → 恢复派发到桌面 1；
4. ws-server 空间不受影响（全部走服务端执行面）；
5. `go test ./...` 全绿。

# 术语表：工作空间 / 项目 / 项目目录

> 状态：**权威真相源（Single Source of Truth）**。任何关于「工作空间」「项目」「项目目录」的命名与语义争议，一律以本表为准。
> 适用端：服务端 `harness_go`（本仓） / 桌面端 `harness_desktop` / 移动端 `harness_mobile`
> 姊妹文档：`docs/工作空间模型与三端能力收口协议.md`、`docs/三端功能矩阵与能力申报对齐表.md`

---

## 0. 为什么需要这张表

`Session` 结构体里同时存在两个**都带 `Workspace` 前缀**的字段：

| 字段 | 实际语义 |
| --- | --- |
| `WorkspaceID` / `workspace_id` | 工作空间（执行面，对应一台设备） |
| `WorkspacePath` / `workspace_path` | **项目目录**（磁盘落盘路径） |

二者**完全无关**，但命名撞车。

**这已经造成过真实误判**：2026-11-12 的需求评审中，曾据「移动端 WebView 会话强制清空 `workspace_path`」推断「工作空间必填会打崩移动端」——实际清空的是**项目目录**，与工作空间无关，该冲突并不存在。

**结论**：注释能解释语义，但救不了误导性的命名。本文档即为该问题的第一道防线。

## 1. 三义权威定义

| # | 术语 | 代码字段 | JSON 键 | 一句话定义 | 决定什么 |
| --- | --- | --- | --- | --- | --- |
| ① | **工作空间** | `Session.WorkspaceID`<br>`Workspace.ID` | `workspace_id` | 顶栏下拉切换的执行面，**对应一台设备**（或服务端内置空间） | 决定**能力天花板**：能否调用工具、工具落在哪台机器 |
| ② | **项目** | `Session.ProjectID`<br>`Project.ID` | `project_id` | 会话的可选归属；纯对话则**无项目** | 决定 `access_mode` 权限快照的继承来源 |
| ③ | **项目目录** | `Session.WorkspacePath`<br>`Project.Path` | `workspace_path` | 项目在磁盘上的**落盘路径** | 决定工具在**哪个目录**下执行 |

### 1.1 关键区分（务必牢记）

- ① 是**逻辑归属**（哪台设备干活），③ 是**物理位置**（在哪台机器的哪个文件夹干活）。
- ① 决定「能不能干」，③ 决定「在哪干」。
- 一个会话**必须**绑定 ①；② 与 ③ 都是可选的。

### 1.2 三者关系

```
会话（Session）
 ├── 工作空间 workspace_id  ← 【必填】执行面，对应一台设备；决定能力天花板
 ├── 项目     project_id    ← 【可选】纯对话则无；决定权限快照来源
 └── 项目目录 workspace_path ← 【可选】磁盘落盘路径；决定工具执行目录
```

## 2. 四类高频混淆场景（避坑清单）

### 2.1 ❌ 把「移动端清空 workspace_path」理解成「清空工作空间」

**代码事实**（`internal/api/handler.go` 建会话处理）：

```go
if h.currentTokenKind(r) == tokenKindWebview {
    req.ProjectID = ""      // 清空项目
    req.WorkspacePath = ""  // 清空【项目目录】，不是工作空间
    req.AccessMode = "confirm"
}
```

`req.WorkspaceID` **从未被清空**。

**正确理解**：WebView 免登会话只是不允许自带项目与磁盘路径，它的**工作空间归属依旧由请求正常决定**。

### 2.2 ❌ 把「工作区宿主」当成「工作空间」

`docs/工作区宿主与目录选择对接约定.md` 中的「**工作区宿主**」指**客户端的目录浏览宿主**（`workspace.list` / `fs.list` 的执行方），是 ③ 的供给侧，**不是** ①。

### 2.3 ❌ 把「服务端内置空间」当成真实设备

`store.BuiltinWorkspaceServerID`（常称 `ws-server`）是一个**逻辑工作空间**，代表「服务端自身执行面」。

- 它是 ① 的一种，**恒在线**，不参与设备在线判定（见 `run_service.go` `resolveToolPolicy`）。
- 它**不在** `devices` 表中，不是可配对设备。
- 其 `RootPath` 为空串，磁盘路径由各会话/项目的 `workspace_path` 提供。

### 2.4 ❌ 把「能力天花板」和「能否对话」混为一谈

| 判定 | 依据 | 结果 |
| --- | --- | --- |
| **能否对话** | 归属设备是否在线 | 离线 → 拒绝发起对话（只读可查看） |
| **能否用工具** | 工作空间 kind + 设备在线 + **有无项目** | 决定 `full` / `readonly` / `none` |

二者是**不同层次**：工作空间必填是「对话准入」，能力天花板是「工具准入」。后者是前者的子集场景，但**不能互相替代**。

### 2.5 ❌ 把「纯对话」理解成「没有工作空间」

**R1 改造后（2026-11-12）**：纯对话**必须**绑定工作空间，缺省绑服务端内置空间（`ws-server`）。

| 会话形态 | workspace_id | project_id | ToolPolicy |
| --- | --- | --- | --- |
| 纯对话 | `ws-server`（必填） | 空 | **readonly** |
| 项目会话（服务端空间） | `ws-server` | 非空 | full |
| 项目会话（设备空间） | 设备工作空间 | 非空 | full / readonly（按 kind） |

**纯对话 = 「有工作空间、但没有项目」**，而不是「没有工作空间」。
`wsID == ""` 已成为应用层不再产生的历史异常态。

## 3. 命名现状与迁移建议

### 3.1 当前命名问题

`WorkspacePath` 这个名字里的 "Workspace" 与 `WorkspaceID` 的 "Workspace" **同形不同义**，是本次误判的直接诱因。

### 3.2 建议的最终命名（尚未执行）

| 现名 | 建议名 | 说明 |
| --- | --- | --- |
| `WorkspacePath` / `workspace_path` | `ProjectDir` / `project_dir` | 语义直指「项目目录」 |
| `WorkspaceID` / `workspace_id` | 保持不变 | 语义无误 |

### 3.3 为何本轮不改名

改名属于**破坏性契约变更**，需要三端同步：

1. **API 层**：`workspace_path` 是对外 JSON 字段，移动端/桌面端均在消费；
2. **DB 层**：`sessions` 表列名变更需数据迁移；
3. **历史数据**：备份包 / 导出 JSON 中已含旧键名，需版本兼容。

**结论**：本轮（术语治理）**只做文档与注释澄清**，不改任何字段名。字段重命名应另立专项计划，在三端协调窗口内统一执行。

## 4. 编码时如何自检

新增/修改涉及「空间」的代码前，先回答三个问题：

1. 我要操作的是**执行面归属**吗？→ 用 `WorkspaceID`（①）
2. 我要操作的是**磁盘路径**吗？→ 用 `WorkspacePath`，并在注释里写明「项目目录」（③）
3. 我要操作的是**项目归属**吗？→ 用 `ProjectID`（②）

**禁止**在注释或文档中用裸词「空间」指代 ③ 或 ②。必须写全「工作空间」/「项目目录」/「项目」。

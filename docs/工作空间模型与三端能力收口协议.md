## 1. 目的与范围

### 1.1 要解决的问题

移动端（`harness_mobile`）的产品定位已收敛为：**基础对话 + 相册上传 + 图片识别**，不承担命令执行。为保证这一约束**由服务端强制、而非前端自觉**，需要在协议层明确三件事：

1. 谁能代表「执行面」，以及执行面的能力如何表达；
2. 会话归属于哪个执行面，能力如何继承；
3. 高危操作被拒绝时，三端各自表现如何。

### 1.2 范围内

- Workspace 的数据模型、三端字段契约；
- 能力判定规则与拒绝语义；
- 会话归属与创建约束；
- 认证与通道标识的最小改动；
- API 契约草案。

### 1.3 范围外（本协议不涉及）

- 目录列举（`workspace.list`）的实现细节 —— 见 `docs/工作区宿主与目录选择对接约定.md`；
- WebView 内部的具体页面改造与窄屏适配；
- 原生审批中心的增删决策细节；
- 移动端 Flutter 代码的具体删减清单。

## 2. 术语与概念分层（**最关键的一节**）

### 2.1 三层实体

```
Workspace（执行面 / 客户端接入）      ← 本文档新增为服务端一等实体
    │  1 : N
    ▼
Project（磁盘受管目录 + 审批规则）     ← 既有实体，新增可选 workspace_id
    │  1 : N
    ▼
Session（对话）                       ← 既有实体，新增可选 workspace_id
```

### 2.2 逐个定义

| 术语 | 定义 | 服务端现状 |
| --- | --- | --- |
| **Workspace** | 一个可承载工作区的**执行面**，或一个已接入的**客户端**。区分维度是 `kind` | ❌ 无表、无路由 |
| **WorkspaceHost** | 能列举本地目录树、承载工作区根的那一方。取值 `server` \| `device:<device_id>` | ✅ 已在 `docs/工作区宿主与目录选择对接约定.md` §1.1 定义 |
| **Project** | 磁盘上受管的一个目录 + 默认控制权限 + 审批规则集合 | ✅ 表 `projects`（迁移 `0008_projects`） |
| **Session** | 一次对话。可归属 Project，也可独立存在（纯对话） | ✅ 表 `sessions` |
| **Device** | 已配对客户端（配对产生，存 `sha256(token)`） | ✅ 表 `devices` |

### 2.3 与既有文档/代码的口径对齐（**差异声明**）

本节声明本文档与既有实现的差异，避免后续实现分歧。

| 对象 | 既有口径 | 本文档口径 | 处理 |
| --- | --- | --- | --- |
| 前端 `Workspace` | 纯前端实体，**不在服务端落库**（`web/src/stores/sessionStore.ts` `persistScope()` 注释明确） | 升格为服务端一等实体 | **本次破例**，需在三端同步 |
| `Project.Workspace` | 前端有 `wsOfProject(p) = p.workspaceId ?? DEFAULT_WORKSPACE_ID`，隔离仅在渲染层 | 落库为真实外键 | 前端推导逻辑需改为读真实数据 |
| `kind` 枚举 | 前端 `WorkspaceKind = 'server' \| 'desktop' \| 'mobile' \| 'browser'`（`web/src/types.ts:10`） | **逐字沿用**，不新增取值 | 无冲突 |
| `Device.Kind` | `desktop \| tablet \| mobile \| cli \| browser`（`internal/model/device.go:8-14`） | **仅作配对登记，不参与能力判定**；`workspaces.kind` 以 `WorkspaceKind` 为准 | 见 §2.4 |
| `WorkspaceHost` | 已定义，`host` 必须与 `workspaceId` 显式绑定并持久化 | **完全沿用**，不重新定义 | 无冲突 |

### 2.4 `Device.Kind` 与 `Workspace.Kind` 的关系（**已定案：不映射，各自独立**）

#### 2.4.1 `DeviceKind` 是什么、用在什么地方（已核实源码）

`DeviceKind` 是**设备配对登记信息**，服务端只在配对链路上使用，共 4 处：

| 用途 | 位置 | 说明 |
| --- | --- | --- |
| 签发配对码时记录声称形态 | `service/device_service.go:179` `IssuePairCode(deviceName, kind)` | 落 `device_pair_codes.device_kind` |
| 端侧完成配对时上报 | `service/device_service.go:200` `PairRequest.Kind` | 落 `devices.kind` |
| 持久化与回读 | `store/repo_device.go:24 / 194 / 223 / 236` | `deviceCols` 含 `kind` |
| 合法性校验 | `model/device.go:17-23` `DeviceKind.Valid()` | 拒绝非法取值 |

**关键事实：`DeviceKind` 目前没有任何一处参与「权限 / 能力 / 工具」判定。** 它只是「这台机器自称是什么」的登记字段。

#### 2.4.2 为什么不做映射（`cli → browser` 已废弃）

两侧语义相反，硬映射会双向出错：

- `docs/三端功能矩阵与能力申报对齐表.md:146`：**浏览器端不作为执行设备注册，不申报任何能力**
- `docs/三端功能矩阵与能力申报对齐表.md:148-151`：存在 `### 4.4 CLI / headless Runner（kind=cli）`，是**可申报能力的执行器**

把 `cli` 映射成 `browser`，等于把「能执行命令的 headless runner」判成「无执行能力的浏览器」，权限判定必然失真。

#### 2.4.3 定案口径

> **两套枚举各自独立，不存在映射关系。**
> - `workspaces.kind` **一律采用 `WorkspaceKind` 的 4 个取值**：`server` / `desktop` / `mobile` / `browser`（**唯一的权限判定依据**）
> - `DeviceKind` 保留现状（配对登记用），**不参与** Workspace 的创建与能力判定

**影响**：若将来出现 `kind = cli` 的执行器，它**不应自动生成 workspace**；如需工作区能力，应在 `WorkspaceKind` 中新增取值后单独启用（见 §11 未决项 1）。当前无 cli 客户端，**不阻塞**。

#### 2.4.4 配对与 Workspace 创建的边界

| 配对形态 | 是否自动创建 Workspace | 说明 |
| --- | --- | --- |
| `desktop` | ✅ 创建 `kind = desktop` | 按 `device_id` 幂等去重，只建一次 |
| `mobile` | ✅ 创建 `kind = mobile` | 按 `device_id` 幂等去重，只建一次 |
| `tablet` / `cli` / `browser` | ❌ 不创建 | 无对应 `WorkspaceKind` 语义，需要时手工创建 |
| —（服务端自身） | ✅ 内置 `kind = server` | 启动时保证存在，`device_id` 为空 |

## 3. 数据模型契约

### 3.1 Workspace（新增，主库 `workspaces` 表）

| 字段 | 类型 | 空值语义 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 必填 | 主键 |
| `name` | string | 必填 | 显示名。内置空间固定为「服务端」，客户端接入时可自定义 |
| `kind` | enum | 必填 | `server` \| `desktop` \| `mobile` \| `browser`，取值同前端 `WorkspaceKind` |
| `device_id` | string | **空 = 服务端内置空间** | 可选外键 → `devices.id`。与 `Device` 为**独立表 + 可选外键**关系（已定案） |
| `root_path` | string | 空 = 未设置工作区根 | 执行面默认工作目录 |
| `created_at` | int64 | 必填 | 毫秒 |
| `updated_at` | int64 | 必填 | 毫秒 |

**派生字段（不落库，查询时组装）**：

| 字段 | 来源 |
| --- | --- |
| `online` | `device_id` 非空 → `device.Hub.Online(device_id)`；`device_id` 空 → 恒 `true` |
| `host` | `device_id` 非空 → `device:<device_id>`；空 → `server` |

> **硬约定**：`online` 仅用于 UI 置灰与提示，**绝不参与能力判定**。能力判定只看 `kind`。

### 3.2 Project（既有，新增一个可选外键）

| 字段 | 变化 | 说明 |
| --- | --- | --- |
| `workspace_id` | **新增，可空** | 空 = 未归属任何工作空间（历史数据兼容） |

其余字段（`id` / `name` / `path` / `default_access_mode` / `pinned` / `deleted_at`）**保持不变**。

### 3.3 Session（既有，新增一个可选外键）

| 字段 | 变化 | 说明 |
| --- | --- | --- |
| `workspace_id` | **新增，可空** | 空 = 纯对话，无执行面 |

**与既有字段的关系（必须点明，避免混用）**：

| 字段 | 含义 | 与 `workspace_id` 的关系 |
| --- | --- | --- |
| `WorkspacePath` | **磁盘路径字符串**，用于拼装系统提示与查 SOP | 与 `workspace_id` **互相独立**，可同时为空或有值 |
| `ProjectID` | 归属项目 | 由 Project 可反推 workspace，但**以 Session 自身 `workspace_id` 为权威** |

> ⚠️ **已知歧义（需在实现前定案）**：`Session.WorkspacePath` 有值而 `WorkspacePath` 与 `ProjectID` 不一致时如何判定。建议：**能力判定只认 `session.workspace_id`**，`WorkspacePath` 仅作提示词与 SOP 输入，不参与权限。

### 3.4 三端字段视图

| 概念 | 服务端（Go） | 桌面端（Rust） | 移动端（Dart） |
| --- | --- | --- | --- |
| 工作空间 | `model.Workspace` | 待定（建议镜像同结构） | 待定（建议仅读，不建） |
| kind 枚举 | `WorkspaceKind`（对齐前端） | 同左 | 同左 |
| 会话归属 | `Session.WorkspaceID` | 只读消费 | 只读消费 |

> **最小化原则**：桌面端与移动端**不自行创建 Workspace**，只消费服务端下发的列表。创建动作仅由服务端或浏览器端（PC）发起。

## 4. 能力判定规则与拒绝语义

### 4.1 唯一判定入口（不允许多处实现）

```
能力天花板 = f(session.workspace_id 所指 Workspace 的 kind)
```

| `workspace.kind` | 允许对话 | 允许工具 | 允许命令/写文件 |
| --- | --- | --- | --- |
| （`workspace_id` 为空，纯对话） | ✅ | ❌ | ❌ |
| `mobile` | ✅ | ❌ | ❌ |
| `server` | ✅ | ✅ | ✅（受审批约束） |
| `desktop` | ✅ | ✅ | ✅（受审批约束） |
| `browser` | ✅ | ✅ | ✅（受审批约束） |

**说明**：

- 「允许工具」为 `❌` 时，工具集在 `Run` 装配阶段即被过滤，模型**根本看不到**这些工具（比事后拒绝更早、更省 token）。
- 「仅支持对话」的工作空间，对话本身、图片识别、历史查看**全部正常**。

### 4.2 拒绝语义（必须与既有审批机制区分）

当 `workspace.kind` 不允许某工具，但模型仍尝试调用时（例如工具曾在历史上下文出现）：

| 维度 | 规定 |
| --- | --- |
| 拒绝层级 | **工具调用级**，不是 `Run` 级 |
| 是否进入 `waiting_approval` | **不进入**。必须在上游短路，否则会触发 `DefaultTimeout = 5min` 的审批等待，超时才算拒绝 |
| 用户可见反馈 | 稳定错误码 + 固定文案「当前为移动端，仅支持对话功能」 |
| `Run` 后续 | **继续执行**，不中断当前对话 |
| 落库 | `tool_events` 记 `denied`，便于审计 |

> **红线段落**：禁止用「等待审批超时」来实现拒绝。那会让用户等 5 分钟才被告知不行，且状态机经历一次无意义的 `waiting_approval` 迁移。

### 4.3 与既有审批机制的关系

| 机制 | 职责 | 本协议立场 |
| --- | --- | --- |
| `Gate.Evaluate` | 判定某工具是否需要人工审批 | **保持不变**，但移动端/纯对话会话在它之前就被短路 |
| `AccessMode` | `confirm`（全部需审）/ `full`（仅 danger 需审） | 移动端会话**强制 `confirm`**，禁止 `full` |
| `strict_approval_device` | danger 审批是否仅限执行端设备 | 保持不变；移动端不参与决策，故不受影响 |

> ⚠️ **必须规避的风险**：若移动端会话被建成 `AccessMode = full`，`gate.go` 中 `write` / `command` 会**自动放行**，连审批都没有。因此「移动端会话强制 `confirm`」是 4.1 之外的第二道防线。

## 5. 会话归属与创建约束

### 5.1 创建规则

| 创建方 | 允许指定 Project | 允许指定 Workspace | 强制约束 |
| --- | --- | --- | --- |
| 移动端（`kind = mobile`） | ❌ 忽略并置空 | 仅可选 `mobile` 或留空 | `workspace_id` 强制为空或 mobile；`AccessMode` 强制 `confirm` |
| 桌面端 | ✅ | ✅ | — |
| 浏览器端（PC） | ✅ | ✅ | — |

### 5.2 「PC 在移动端工作空间内创建会话」如何判定（**核心场景**）

这是本协议要回答的关键问题。规定：

> **能力天花板由 `session.workspace_id` 所指 Workspace 的 `kind` 决定，与创建者是谁无关。**

| 场景 | session.workspace_id | 生效能力 |
| --- | --- | --- |
| PC 在 `mobile` 工作空间内建会话 | 该 mobile 空间 | **仅对话** |
| 手机在 `desktop` 工作空间内建会话 | 该 desktop 空间 | 全工具（受审批） |
| 手机建会话但不选工作空间 | 空 | 仅对话 |
| PC 建会话不选工作空间 | 空 | 仅对话 |
| **存量老会话（迁移后）** | **回填到服务端内置空间** | **维持全工具**（见 §9.1） |

**理由**：WorkSpace 的 `kind` 表达的是**执行面能力**，不是创建者身份。隔离区就是隔离区，任何端进入都不突破——否则标记可被绕过，形同虚设。

> ✅ **已定案**：采用此「取 workspace 严」的口径，**不再**引入「取更严格者」的二次比较。因为 `session.workspace_id` 已是唯一权威来源，不需要与创建端做比较。

### 5.3 服务端必须强制的校验（不能只靠前端）

| 校验点 | 要求 |
| --- | --- |
| `POST /api/v1/projects` | 创建方为移动端 → 403 |
| `POST /api/v1/sessions` | 创建方为移动端 → 强制忽略 `project_id`、强制 `workspace_id ∈ {空, mobile}`、强制 `access_mode = confirm` |
| `PATCH /api/v1/sessions/{sid}` | 不可将已有会话迁入 `mobile` 工作空间（防止提权反向操作） |

> **理由**：移动端与 PC 共用同一套 Web UI，前端隐藏按钮**必然可被直连 API 绕过**。安全约束必须在服务端 API 层实现。

## 6. 认证与通道标识

### 6.1 配对阶段（已具备，字段已存在）

移动端壳在配对请求中上报 `kind`：

```
POST /api/v1/devices/pair
Body: { pair_code, name, kind: "mobile", platform, capabilities[] }
```

`Device.Kind` 已含 `DeviceKindMobile`（`internal/model/device.go:11`），**无需新增字段**。

服务端据此：

- 落户 `Device.Kind = mobile`；
- **自动创建（或复用）一个 `kind = mobile` 的 Workspace**，`device_id` 指向该设备。

### 6.2 请求身份判定（**本协议的未决重点**）

服务端需要知道「当前请求来自哪类端」以执行 §5.3 的校验。三种候选：

| 方案 | 做法 | 可靠性 | 评价 |
| --- | --- | --- | --- |
| A | 请求体自报 `client_kind` | ❌ 可伪造 | **禁止** |
| B | 移动端壳配对得到的 `device_token` 走 Bearer | ✅ 不可伪造 | **推荐** |
| C | WebView 一次性 ticket 携带 `channel` | ✅ 不可伪造 | 与 B 可并存 |

> **推荐**：优先 B（设备令牌 Bearer），因为移动端壳本身已配对、已有 `device_token`；WebView 场景补充 C，用短时 ticket 把 `device_id` 绑定到浏览器会话。

**硬约束**：判定依据必须是**服务端可验证的凭据**，绝不可信任客户端声明的字符串。

### 6.3 与既有 `publicPaths` 的关系

若新增 ticket 交换端点，必须显式加入 `internal/api/router.go` 的 `publicPaths` 并写明理由（现有：`auth/login`、`auth/sso`、`devices/pair`、`devices/ws`）。

## 7. API 契约草案

> 以下为协议草案，最终以 `internal/api/router.go` 注册为准。

| 方法 | 路径 | 说明 | 鉴权 |
| --- | --- | --- | --- |
| `GET` | `/api/v1/workspaces` | 列出工作空间（含派生 `online` / `host`） | 需登录 |
| `POST` | `/api/v1/workspaces` | 创建（**移动端 403**） | 需登录 |
| `GET` | `/api/v1/workspaces/{wid}` | 详情 | 需登录 |
| `PATCH` | `/api/v1/workspaces/{wid}` | 改名 / 改 `root_path`（**`kind` 不可改**） | 需登录 |
| `DELETE` | `/api/v1/workspaces/{wid}` | 删除（有关联会话时拒绝，或要求显式迁移） | 需登录 |

**`kind` 不可修改的理由**：`kind` 是权限天花板的依据。若允许从 `mobile` 改成 `desktop`，等于一次提权操作，会让历史会话的能力被静默放大。

### 7.1 响应示例

```json
{
  "items": [
    { "id": "ws-server", "name": "服务端", "kind": "server", "device_id": "", "online": true, "host": "server" },
    { "id": "ws-dev-1", "name": "我的手机", "kind": "mobile", "device_id": "dev-1", "online": true, "host": "device:dev-1" }
  ]
}
```

## 8. 三端职责矩阵

## 9. 兼容与迁移

### 9.1 历史数据与回填策略（**已定案：全部回填到「第一个服务端 Workspace」**）

#### 9.1.1 定案结论

> **存量 `sessions` 与 `projects` 的 `workspace_id` 一律回填到服务端内置空间 `ws-server`（`kind = server`）。**

| 数据 | 处理 |
| --- | --- |
| 服务端内置空间 | 迁移时**先行创建** `ws-server`（`kind = server`、`device_id = ''`），作为回填目标 |
| 既有 `projects`（`workspace_id` 为 NULL） | 回填为 `ws-server` |
| 既有 `sessions`（`workspace_id` 为 NULL） | 回填为 `ws-server` |
| 前端既有 mock 工作空间 | 首次拉取 `/workspaces` 后以服务端数据为准覆盖 |

#### 9.1.2 为什么这样定（依据当前真实状态）

`run_service.go:292-293` 显示当前所有 Run 的执行面：

```go
LeaseHolder:     deviceID, // 空串 = 服务端本地执行面
RequesterDevice: deviceID,
```

**当前并不存在跑在客户端设备上的会话，全部由服务端本地执行。** 因此回填到 `ws-server` 是**如实记录现状**，而不是放宽权限。

若回填为 `NULL`，这些会话会被判为「纯对话」，导致老用户升级后发现「老对话不能执行命令了」——那是能力倒退事故，不可接受。

#### 9.1.3 迁移执行顺序（**顺序不可颠倒**）

```sql
-- ① 先建表（0009_workspaces）
CREATE TABLE workspaces (...);

-- ② 再插内置空间（必须在回填之前，否则外键悬空）
INSERT INTO workspaces(id, name, kind, device_id, root_path, created_at, updated_at)
VALUES ('ws-server', '服务端', 'server', '', '', <now>, <now>);

-- ③ 加列（SQLite ALTER TABLE ADD COLUMN 允许可空列）
ALTER TABLE projects ADD COLUMN workspace_id TEXT;
ALTER TABLE sessions ADD COLUMN workspace_id TEXT;

-- ④ 最后回填
UPDATE projects SET workspace_id = 'ws-server' WHERE workspace_id IS NULL;
UPDATE sessions SET workspace_id = 'ws-server' WHERE workspace_id IS NULL;
```

> ⚠️ **反向风险**：若先回填后建 `ws-server`，会写入悬空外键；若中途失败可重跑，但**建表与插入必须幂等**（`CREATE TABLE IF NOT EXISTS` / `INSERT OR IGNORE`）。

#### 9.1.4 迁移后行为确认

| 对象 | 迁移后能力 | 是否符合预期 |
| --- | --- | --- |
| 老会话（`ws-server`） | 全工具（仍受审批约束） | ✅ 无倒退 |
| 老项目（`ws-server`） | 正常 | ✅ |
| 新建移动端会话 | 仅对话 | ✅ |
| 用户手动把会话迁到 `mobile` 空间 | 收窄为仅对话 | ✅ 显式操作，非静默 |

### 9.2 工程铁律（实现时必须遵守）

`internal/store/repo_main.go:49-53` 有明确约定：

> `sessionColumns` 与 `SessionRepo.Create` 的列清单、`scanSession` 的 Scan 实参**必须三处严格同步**（顺序一致），漏改一处即静默错列。

新增 `workspace_id` 到 `sessions` 表时，**必须同时修改这三处**，否则不报错但数据全乱。

### 9.3 迁移编号

现有迁移已到 `0008_projects`，本次新增应为 `0009_*`（workspaces 表）与后续编号。新增外键列若独立成一个迁移，需注意 SQLite 的 `ALTER TABLE` 限制。

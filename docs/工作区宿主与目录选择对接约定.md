# harness_go 工作区宿主与目录选择对接约定

> 版本：v0.2（对接约定草案）　日期：2026-11-09
> 定位：把「项目目录选择」从**手填文本框**升级为**可视化目录选择**，并明确该能力由「工作区宿主」按空间隔离提供。
> 状态：**L0（服务端宿主）已实现**（`internal/api/fs_handler.go` + `web/src/components/DirectoryPicker.tsx`）；**L1/L2（客户端宿主）为未来 harness_desktop / harness_mobile 的前置契约**，本期只登记、不实现。
> 关联文档：`docs/多端协同架构可行性方案.md`、`docs/protocols.md`、`docs/系统内置工具可安装性与多端协同.md`、`docs/架构设计文档.md`
> 关联约束：`internal/device/*`（设备网关与派发器）、`internal/api/router.go`

## 0. 结论速览

| 议题 | 结论 | 置信度 |
| --- | --- | --- |
| 当前是否支持选择目录 | **不支持**。所有目录入口均是手填文本框，服务端无任何目录列举路由 | 高 |
| 「切到哪个工作空间就只能选那个空间的目录」 | **可行**，但需引入「工作区宿主」抽象；现有 `Workspace` 是纯前端实体，不具备宿主语义 | 高 |
| 浏览器端与桌面端走同一条流程 | **可行**。做法是让服务端也套一层同形 API，前端只认 `host` 参数 | 高 |
| 是否复用 `device.Dispatcher` 派发目录列举 | **可复用，但必须改 4 处语义**（强制指定设备、禁止降级、短超时、旁路幂等缓存），否则会污染 task 生命周期 | 中高 |
| 是否新造能力标签 | **不需要**。复用 `docs/protocols.md:38` 既有 `workspace.read` 命名风格，新增 `workspace.list` | 高 |

**一句话**：目录能力不属于「窗口形态（浏览器/桌面/移动）」，而属于「**在启动中的宿主**（服务端或某个在线客户端）」。前端只调一个接口，`host` 决定本地直连还是远程派发。

## 1. 术语与模型

### 1.1 工作区宿主（WorkspaceHost）

**定义**：能够列举本地目录树、并承载「工作区根」的那一方。

| 宿主类型 | `host` 取值 | 列举方 | 在线真值来源 |
| --- | --- | --- | --- |
| 服务端宿主 | `server` | 服务端进程自身 | 恒在线（服务端活着即在线） |
| 客户端宿主 | `device:<device_id>` | 该客户端进程 | `device.Hub.Online(id)` + 心跳 |

### 1.2 与现有 `Workspace` 的关系（**不要混淆，这是最关键的一节**）

现有前端 `Workspace`（`web/src/stores/sessionStore.ts`）是一个**纯前端实体**：
- `persistScope()` 的注释明确写着：项目 / 工作空间 / 当前空间「都是纯前端实体，不在服务端落库，只能靠本地存储」；
- `WorkspaceSwitcher.tsx:15-19` 的 `KIND_OPTIONS` = `desktop / mobile / browser`，另有内置服务端空间；
- `wsOfProject(p) = p.workspaceId ?? DEFAULT_WORKSPACE_ID` 的隔离**只发生在渲染层**。

因此本期引入的映射是：

```
Workspace（前端实体，1:1） ──→ WorkspaceHost（能力提供方）
   ws.server  → host = "server"
   ws.<端>    → host = "device:<device_id>"
```

**硬约定**：`host` 与 `workspaceId` 必须在 Workspace 实体上显式绑定并持久化。禁止在运行时「按在线情况自动挑一个宿主」——那会导致同一空间在不同时间列出不同机器的目录。

### 1.3 与「目录选择」的关系

目录选择器只接受 `host`，绝不自己猜：

```
DirectoryPicker(host, path)  ──→  list(host, path)  ──→  { parent, dirs[], separator }
```

## 2. 可行性判定（已核实事实）

### 2.1 支持本方案的可复用资产

| 资产 | 位置 | 复用于本方案 |
| --- | --- | --- |
| 设备长连接 + 心跳 + 在线表 | `internal/device/gateway.go:298/314`（`hub.Beat`）、`internal/device/hub.go`（`Online` / `IDs`） | 「该客户端是否在启动中」的**唯一真值来源** |
| 协议信封与版本协商 | `internal/device/protocol.go`（`Envelope` / `Valid()` / `CompatibleVersion`） | 帧格式无需重造 |
| 通用请求/应答派发器 | `internal/device/dispatcher.go`（`Dispatch` / `candidates` / `ErrDeviceUnavailable`） | 远程列举的执行机 |
| 执行面归属模型 | `internal/agent/engine.go:140-145`（`LeaseHolder` / `RequesterDevice`）、`model.ExecutorServer` / `model.ExecutorDevice` | 「这个目录是谁列举的」有字段表达 |
| 能力标签词汇 | `docs/protocols.md:38`（`workspace.read` / `workspace.write`） | 新增 `workspace.list` 与既有命名一致 |
| 端能力上报 | `internal/api/device_handler.go:46`（`capabilityInput{Name, Version}`） | 能力协商的载体已存在 |
| 前端空间切换 UI | `web/src/components/WorkspaceSwitcher.tsx`（含 `online` 判定与「该工作空间离线」提示，`layout/Sidebar.tsx:163-168`） | 离线禁用逻辑可原样复用 |

### 2.2 必须解决的四个坑

| # | 坑 | 说明 | 对策 |
| --- | --- | --- | --- |
| 1 | **在线 ≠ 有列举能力** | 客户端可能在线但未实现 `fs.list`，直接派发会超时或报「工具未实现」 | 派发前查该设备是否申报 `workspace.list`；未申报则**前端直接禁用**该空间的选择器 |
| 2 | **`Dispatcher.candidates()` 会回退到「任一在线设备」** | `dispatcher.go:356-379` 在未指定 `DeviceID` 时按 ID 排序取在线设备 | 目录列举**强制指定 `DeviceID`**；该设备不在线即明确报错，**禁止换机** |
| 3 | **`ErrDeviceUnavailable` 的「静默降级本地执行」约定** | `dispatcher.go:67-68` 明确要求调用方静默降级 | 目录列举**必须显式例外**：不许降级到服务端本地，否则会把服务端目录列给客户端空间 |
| 4 | **task 生命周期与审计污染** | `TaskRequest.ToolEventID` 是幂等键且被注释为「落库主键」（`dispatcher.go:75-79`）；`dispatchHistory` 有 256 条 / 5 分钟 TTL 缓存 | 目录浏览是**高频、非审计**操作，**不得**走工具事件落库链路。见 §3.4 |

## 3. 统一契约

### 3.1 前端唯一入口

```ts
// web/src/lib/workspaceHost.ts（新增）
export type HostID = 'server' | `device:${string}`

export interface DirEntry {
  name: string        // 目录名（末段）
  path: string        // 绝对路径（宿主本地口径）
  writable?: boolean  // 可选：宿主是否有写权限（未提供则不显示）
}

export interface DirListing {
  parent: string | null  // 上级目录；null = 已在根
  path: string           // 当前目录
  separator: '\\' | '/'  // 用于面包屑切分（Windows / POSIX）
  roots: DirEntry[]      // 仅在根层级给出（盘符 / 挂载点 / 工作区根）
  dirs: DirEntry[]       // 子目录（只列目录，不列文件）
}

export interface WorkspaceHost {
  id: HostID
  online: boolean
  canList: boolean     // 是否具备 workspace.list 能力
  list(path: string): Promise<DirListing>
}
```

**关键设计**：`DirectoryPicker` 组件只依赖 `WorkspaceHost`，**服务端宿主与客户端宿主在 UI 侧完全同形**，这就是「浏览器和客户端走同样流程」的落地方式。

### 3.2 HTTP 契约（统一入口，服务端做路由分流）

```http
GET /api/v1/fs/roots?host=server                 → { roots: DirEntry[] }
GET /api/v1/fs/dirs?host=server&path=D:/Work     → DirListing
GET /api/v1/fs/dirs?host=device:dev-abc&path=D:/Work  → DirListing（服务端转发）
```

- `host=server` → 服务端就地列举（**L0，本期实现**）
- `host=device:<id>` → 服务端经设备通道派发（**L1，待客户端就绪**）
- 错误统一走既有 `apperr` 编码：

| 场景 | HTTP | `apperr` Code |
| --- | --- | --- |
| 设备不在线 | 409 | `fs.host_offline` |
| 设备未申报列举能力 | 409 | `fs.host_unsupported` |
| 路径越界 / 非法 | 400 | `fs.path_denied` |
| 路径不存在或非目录 | 404 | `fs.path_not_found` |
| 端侧超时 | 504 | `fs.host_timeout` |

> **设计取舍**：为什么不让前端直连设备？因为设备是**反向长连接**（端 → 服出站 WS，见 `device_handler.go:141-148` 注释，鉴权靠 `device_token`），浏览器无法直连，且强行直连会把设备令牌暴露给浏览器。**服务端必须做代理**。

### 3.3 客户端下发契约（L1，待实现）

复用 `device.Envelope`，新增两种帧类型（或复用通用 task 帧，见 §3.4 的取舍）：

```json
// 服务端 → 客户端
{ "v": 1, "type": "fs.list", "id": "<req_id>", "ts": 0,
  "payload": { "path": "D:/Work", "with_roots": false } }

// 客户端 → 服务端
{ "v": 1, "type": "fs.list.result", "id": "<req_id>", "ts": 0,
  "payload": { "path": "D:/Work", "parent": "D:/", "separator": "\\",
               "roots": [], "dirs": [{ "name": "Proj", "path": "D:/Work/Proj" }] } }
```

**客户端实现要求（写进 harness_desktop / harness_mobile 的验收项）**：

1. **只列目录**：`dirs` 只允许返回目录项，不得返回文件名（防止目录选择器变成文件浏览器，扩大信息暴露面）；
2. **不读文件内容**：实现中禁止任何 `os.ReadFile` / `fs.readFile`，只允许 `readdir` 元数据；
3. **路径归一**：返回的 `path` 必须是宿主本机的绝对路径，且已 `Clean` 过；`separator` 必须如实上报（Windows `\`，POSIX `/`）；
4. **拒绝上跳越界**：当 `parent` 已到根时，`parent` 必须返回 `null`，不得返回 `".."`；
5. **符号链接策略**：默认不跟随（避免环与越界）；若跟随，必须校验解析后的真实路径仍在允许根内；
6. **超时自守**：单次列举必须在 **3 秒**内返回，大目录需分页或截断并在响应中标注 `truncated: true`；
7. **能力申报**：在设备 hello/ping 的 `capabilities` 中上报 `workspace.list`，否则前端会把该空间置灰。

### 3.4 复用 `Dispatcher` 的取舍（实现前必须定案）

`Dispatcher.Dispatch()` 能直接完成「服务端 → 指定客户端 → 等结果」，但有两点语义不适配：

- `TaskRequest.TaskID` / `ToolEventID` 被设计为**工具事件幂等键**（`dispatcher.go:75-79` 注释「落库主键」），而目录浏览是高频非审计操作；
- `dispatchHistory` 只有 **256 条 / 5 分钟**（`dispatcher.go:60-62`），用户连点目录会迅速冲掉正常工具任务的幂等缓存。

**方案 A（推荐）**：为 Dispatcher 增加 `Ephemeral: bool` 字段，设为 true 时**跳过 `history` 幂等缓存与 task 记账**，仅复用「候选选择 + 帧写出 + 终态等待 + 超时收敛」。
**方案 B**：在 `internal/device` 下新增独立的 `PathQuery` 轻量 RPC（不复用 task 结构）。

> 建议 A：改动面小、复用度高。**无论哪种方案，都必须确认该链路不经过 `engine` 的 `InsertToolEvent`**（`internal/agent/engine.go` 中工具事件落库在 engine 侧完成，Dispatcher 本身不落库）。否则每次点开目录都会产生一条工具事件，直接污染 `GET /api/v1/audit/tool-events` 与日志统计。

## 4. 安全守卫（L0 与 L1 共用口径）

目录列举是**信息暴露面**，必须默认收紧：

1. **只读**：仅 `readdir` 元数据，不返回文件内容、不返回文件大小之外的可疑元数据；
2. **令牌鉴权**：`/api/v1/fs/*` 挂用户令牌中间件（非 `publicPaths`）；
3. **路径白名单**：默认仅允许服务端工作区根（`HARNESS_DATA_DIR` 同级的工作区根）及其子树；用环境变量 `HARNESS_FS_ROOTS`（分号分隔）放开额外根；
4. **穿越防护**：`filepath.Clean` + 拒绝含 `..` 段的输入 + `filepath.Rel` 校验结果不以 `..` 开头；
5. **审计**：只审计**跨根访问**与**拒绝事件**，不审计每次正常浏览（避免日志噪音）；
6. **跨端信任**：端侧返回的目录结果 `SourceTrust` 恒为 `untrusted`，前端只能用于「填充输入框」；项目 `path` 落库前**服务端必须再做一次存在性校验**，不得因「端侧列出来的」而免检。
